# AssetReplay Constitution

AssetReplay는 1995년 이후의 다중 자산군 히스토리 데이터를 축적하고, 특정 시점의 가격을 조회하며,
자산 간 투자 성과를 재현·비교 시뮬레이션하는 웹 애플리케이션이다.

## 프로젝트 정체성 및 도메인 범위

- **Role**: 각종 자산을 시뮬레이션해서 최선의 투자처를 알려줄 수 있는 풀스택 개발자
- **Goal**: 상용 소프트웨어 수준의 UI/UX와 안정성을 갖춘 자산 시뮬레이션 플랫폼 구축
- **Philosophy**: "데이터 정합성", "비동기 처리", "계산 재현성", "모듈화"를 최우선 가치로 둔다
- **Approach**: 단계적 개발로 뼈대부터 구축하고, 자산군을 하나씩 확장한다

| # | 자산군 | 축적 대상 | 기준 시작일 |
|---|--------|-----------|-------------|
| 1 | 외환(FX) | USD, JPY, EUR 대원화 환율 일별 데이터 | 1995-01-01 |
| 2 | 가상자산 | BTC, ETH 등 일별 OHLCV | 2010-01-01 |
| 3 | 부동산 | 아파트 실거래가(지역/단지/전용면적별) | 확보 가능 최초 시점 |
| 4 | 주식·ETF·지수 | KOSPI, KOSDAQ, NASDAQ, DOW, NIKKEI의 종목별 OHLCV, 배당락일·배당금 이력, 지수·ETF 시계열 | 확보 가능 최대 기간 |
| 5 | 예금 | 시중은행·저축은행 예금/적금 금리 이력 | 확보 가능 최초 시점 |

자산군 4의 배당 이력과 5의 금리 이력은 각각 배당 재투자 복리효과와 예금 복리효과 계산의
입력이므로, 가격 시계열과 동등한 정합성 요구를 받는다.

## Core Principles

핵심 원칙은 아래 9개로 한정하며, 개수를 늘리지 않는다.
각 원칙은 코드 리뷰에서 위반 여부를 판정할 수 있는 규칙으로만 구성한다.

### I. 비동기 우선 (Async-First)

- HTTP 요청은 `asyncio` + `aiohttp`를, DB 접근은 `aiomysql`을 사용해야 한다(MUST).
- 요청 처리 경로에서 동기 블로킹 호출(`requests`, 동기 DB 드라이버, `time.sleep`)을 금지한다(MUST NOT).
- 불가피한 블로킹 작업은 `run_in_executor`로 격리해야 한다(MUST).

**Rationale**: 5개 자산군 × 수천 종목 × 30년치 수집은 네트워크 대기가 지배적이다.
동기 호출 하나가 이벤트 루프를 막으면 수집 처리량과 API 응답성이 동시에 무너진다.

### II. 데이터 소스 격리와 복원력

- 데이터 소스는 교체 가능한 어댑터로 구현해야 한다(MUST). 특정 벤더(키움 REST API, 공공데이터포털,
  거래소 API, 한국은행 ECOS 등)의 타입·응답 형식이 도메인 계층에 노출되면 위반이다.
- `asyncio.Semaphore`로 소스별 동시 호출 수를 제한하고 각 API의 호출 제한을 준수해야 한다(MUST).
- 실패 시 지수 백오프 + 지터를 적용해야 한다(MUST).
- 소스별 rate limit, 인증 방식, 재시도 정책은 코드가 아닌 설정으로 선언해야 한다(MUST).
- API 키·시크릿은 코드 및 저장소에 하드코딩하지 않고 환경변수로 주입해야 한다(MUST NOT hardcode).
- 각 데이터 소스의 이용약관·라이선스를 준수하고 출처를 문서에 명시해야 한다(MUST).

**Rationale**: 데이터 소스는 우리가 통제할 수 없는 유일한 구성 요소다. 어댑터로 격리해야
소스 교체 시 도메인 로직이 함께 무너지지 않고, 유량 제한 위반은 키 차단으로 수집을 중단시킨다.

### III. 테스트 주도 개발 (TDD) [필수 / NON-NEGOTIABLE]

- 테스트 작성 → 사용자 승인 → 테스트 실패 확인 → 구현 순서를 준수해야 한다(MUST).
- 구현보다 테스트가 먼저 커밋되고, 최초 실행에서 실패함을 확인해야 한다(MUST).
- 커버리지 80% 이상을 유지해야 한다(MUST). 미만이면 머지를 차단한다.
- 단위·통합·외부 API 계약(contract) 테스트를 모두 작성해야 한다(MUST).
- 외부 API는 저장된 응답 픽스처로 검증하며, 전체 스위트는 네트워크 없이 통과해야 한다(MUST).

**Rationale**: 금융 계산 오류는 결과가 그럴듯해 사람 눈에 띄지 않는다. 테스트만이 30년치
복리 계산의 정확성을 지속적으로 보증한다. 네트워크 없는 통과 요건은 외부 장애로부터 CI를 지킨다.

### IV. 모듈화 설계

- 단일 책임 원칙(SRP), 의존성 주입(DI), Protocol 기반 인터페이스를 적용해야 한다(MUST).
- 계층을 분리해야 한다(MUST): 수집(ingestion) / 저장(repository) / 도메인 계산(simulation) / API / UI.
- 도메인 계산 계층은 DB·HTTP에 의존하지 않는 순수 함수여야 한다(MUST).
  DB나 HTTP 없이 단독 테스트가 불가능한 계산 코드는 위반이다.
- 상위 계층은 하위 계층의 구체 구현이 아닌 Protocol에 의존해야 한다(MUST).

**Rationale**: 원칙 III의 순수 함수 단독 테스트와 원칙 II의 어댑터 교체는 계층 분리를 전제한다.
계층이 섞이면 두 원칙이 동시에 무력화된다.

### V. 데이터 정합성과 재현성 (Data Integrity & Reproducibility)

저장된 값이 "무엇을, 언제, 어느 기준으로" 뜻하는지 모호해서는 안 되며, 같은 질의는 언제
실행해도 같은 값을 반환해야 한다.

- 원본(raw) 응답을 보존하고, 정규화된(normalized) 시계열과 분리 저장해야 한다(MUST).
- 모든 수집은 멱등(idempotent)하고 중단 후 재개 가능(resumable)해야 한다(MUST).
  시계열 테이블은 (자산 식별자, 날짜) 복합 유니크 키 + upsert로 멱등성을 보장해야 한다(MUST).
- 모든 시계열 레코드는 `source`와 `ingested_at`을 기록해야 한다(MUST).
- 백필과 증분 수집을 구분하고, 자산군별 수집 커버리지를 조회할 수 있어야 한다(MUST).
- 주가는 수정주가와 원주가를 구분 저장하고, 액면분할·병합·유상증자를 명시 반영해야 한다(MUST).
- 휴장일·결측치는 명시적으로 표현해야 한다(MUST). 임의 보간과 전일 값 자동 복사를 금지한다(MUST NOT).
  보정이 필요하면 규칙을 문서화하고 별도 컬럼으로 표시해야 한다(MUST).
- 시각은 UTC로 저장하고 표시 시점에 거래소 현지 시간대(KST/EST/JST)로 변환해야 한다(MUST).
- 일별 시계열의 "날짜"는 해당 거래소 거래일 기준임을 명시하고, 거래소별 캘린더로 휴장일을
  판정해야 한다(MUST). 가상자산 일봉 기준 시각은 UTC 00:00으로 명시해야 한다(MUST).
- 자산 간 비교 시 기준 통화를 명시하고, 환산 환율의 날짜와 출처를 결과에 포함해야 한다(MUST).

**Rationale**: 과거 데이터를 신뢰할 수 있게 재현하는 것이 이 프로젝트의 존재 이유다.
수정주가와 원주가를 섞거나 결측치를 조용히 보간하면 수익률이 틀리고도 그럴듯해 보인다.
멱등성은 30년치 백필이 중간에 실패해도 처음부터 다시 받지 않게 해준다.

### VI. 금융 계산 정확성 (Financial Accuracy)

- 모든 금액·수익률·환율 계산에 `Decimal`을 사용해야 한다(MUST). `float`을 금지한다(MUST NOT).
- DB의 금액·비율 컬럼은 `DECIMAL`을 사용해야 한다(MUST). `FLOAT`/`DOUBLE`을 금지한다(MUST NOT).
- 배당 재투자 복리, 예금 복리, 환산 수익률 등 모든 계산식은 검증된 참조값 테스트를
  동반해야 한다(MUST).
- 세금·수수료·배당 원천징수 등 가정은 코드에 숨기지 않고 명시적 파라미터로 노출·문서화해야 한다(MUST).
- 시뮬레이션 결과는 입력 파라미터와 데이터 스냅샷 기준으로 재현 가능해야 한다(MUST).

**Rationale**: 30년 복리 계산에서 부동소수점 오차는 누적되어 유의미한 금액 차이를 만든다.
가정을 숨기면 사용자는 자신이 무엇을 비교하는지 알 수 없어 결과를 신뢰할 수 없다.

### VII. 반응형 UI 및 진행 상황 가시화

- Zustand 기반 반응형 상태 관리를 적용해야 한다(MUST).
- 장시간 수집 작업과 시뮬레이션의 진행률을 WebSocket 또는 SSE로 실시간 스트리밍해야 한다(MUST).
- 시계열 차트는 Lightweight Charts로 렌더링해야 한다(MUST).
- 수만 건 이상의 데이터 포인트에서도 응답성을 유지하기 위해 다운샘플링 또는 가상화를
  적용해야 한다(MUST).

**Rationale**: 30년치 백필은 수 분에서 수 시간이 걸린다. 진행률이 보이지 않으면 사용자는
앱이 멈춘 것으로 판단하며, 상용 수준 UX라는 목표는 이 가시성 없이 달성되지 않는다.

### VIII. 한국어 문서화

- 코드 주석, docstring, 커밋 메시지, 설계 문서를 한국어로 작성해야 한다(MUST).
- 기술 용어, 라이브러리명, API 식별자, 코드 심볼은 원어를 유지해야 한다(MUST).

**Rationale**: 작업 언어를 하나로 고정해야 설계 의도가 번역 손실 없이 전달된다.
식별자를 원어로 두는 것은 코드와 문서 사이의 검색 가능성을 보존하기 위해서다.

### IX. MVP 중심 점진적 개발

- 뼈대를 먼저 구축하고 반복적으로 확장해야 한다(MUST).
- YAGNI 원칙을 준수해야 한다(MUST): "현재 필요하지 않은 기능은 구현하지 않는다."
- 자산군은 한 번에 하나씩 완결해야 하며(MUST), 확장 순서는
  FX → 가상자산 → 주식/ETF/지수 → 예금 → 부동산으로 한다.
- 각 자산군 단계는 조회 API와 UI까지 동작하는 수직 슬라이스로 완성해야 한다(MUST).
  여러 자산군의 수집 계층만 먼저 만들고 UI를 미루는 것은 위반이다.

**Rationale**: 자산군마다 데이터 소스, 시간 기준, 결측 패턴이 다르다. 하나를 끝까지 관통해봐야
재사용할 추상화가 무엇인지 알 수 있다. 부동산이 마지막인 이유는 지역/단지/면적 축의 비정기
거래 데이터라 나머지 4개의 균일한 일별 시계열과 형태가 근본적으로 달라, 스키마 안정 후
통합하는 것이 안전하기 때문이다.

**데이터베이스 운영 규약**

- 스키마 변경은 마이그레이션 스크립트로 관리해야 한다(MUST). 수동 DDL을 금지한다(MUST NOT).
- 금액·비율 컬럼 타입은 원칙 VI를, 시계열 유니크 키는 원칙 V를 따른다.

**크로스 플랫폼 요구사항**

- Windows 11, Linux, macOS에서 동일하게 동작해야 한다(MUST).
- 플랫폼 종속 코드는 어댑터로 분리해야 한다(MUST).
- 파일 경로는 `pathlib`을 사용해야 한다(MUST). 하드코딩된 경로 구분자를 금지한다(MUST NOT).

## Governance

- 본 헌법은 다른 모든 관행에 우선한다. 충돌하는 관행·문서·설정은 무효다.
- 모든 PR과 리뷰는 헌법 준수 여부를 검증해야 한다(MUST).
- 원칙을 위반해야 하는 경우 그 복잡성을 정당화하고 근거를 문서에 남겨야 한다(MUST).
  정당화 없는 위반은 머지를 차단한다.
- 개정은 문서화, 승인, 마이그레이션 계획을 필수로 한다(MUST).
- 새로운 규칙은 원칙을 늘리기보다 기존 9개 원칙 또는 제약 섹션에 편입하는 것을 우선 검토해야 한다(MUST).
- 버전 관리는 유의적 버전(Semantic Versioning)을 따른다.
  - **MAJOR**: 원칙의 삭제 또는 재정의 등 하위 호환이 깨지는 변경
  - **MINOR**: 새로운 원칙 또는 섹션 추가, 지침의 실질적 확장
  - **PATCH**: 문구 명확화, 오타 수정, 의미를 바꾸지 않는 다듬기
