# 평가: 외환 화면의 낡은 날짜 표시와 통화 탭 식별 불가

## 보고 내용

1. 오늘은 2026-09-27인데 요약 카드가 **2020-12-01 기준**을 보여준다. 오늘 날짜가 나와야 한다.
2. 특정일 검색에서 **오늘을 눌러도 2020년 날짜가 유지된다.**
3. 미국 달러가 기본 선택인 것 같은데 **선택 표시가 보이지 않아** 알 수 없다.

## 진단 결과

세 건은 **원인이 서로 다르다.** 하나는 환경 오염, 하나는 그 증상, 하나는 진짜 UI 결함이다.

### #1 — 데이터 오염 (애플리케이션 결함 아님)

개발 DB에 **통합 테스트의 스텁 데이터만** 들어 있다.

```
fx_rate: 12행, USD만, 2020-01-01 ~ 2020-12-01, 전부 1200.000000
서로 다른 환율 값: 1개
커버리지: USD 2020-01-01 ~ 2020-12-31
```

이 값은 `backend/tests/integration/conftest.py`의 스텁과 정확히 일치한다.

```python
QUOTES = {"USD": [(f"2020-{m:02d}-01", "1200.00") for m in range(1, 13)]}
```

통합 테스트가 `reset_schema()`로 **모든 테이블을 드롭·재생성**한 뒤 스텁 행을 쓴다. 개발
DB와 테스트 DB가 같은 MySQL 데이터베이스를 공유해 실제 수집분이 날아갔다.

**화면은 정상 동작하고 있다.** 002 명세는 "오늘 잠정값이 있으면 그것을, 없으면 마지막
확정값을 제시하고 어느 쪽인지 표시한다"고 정한다. 마지막 확정값이 2020-12-01이므로
`확정 · 2020-12-01 기준`은 **요구사항대로의 결과**다.

### #2 — #1의 증상 + UX 논점 (부분적으로 실제 결함)

`frontend/src/stores/fxWorkspaceStore.ts`의 `selectDate`가 범위 밖 선택을 **거절하고
이전 날짜를 유지**한다.

```ts
const notice = checkRange(date, cov);
if (notice) {
  set({ notice });
  return;              // selectedDate를 바꾸지 않는다
}
```

커버리지가 2020-12-31까지이므로 오늘(2026-09-27)은 범위 밖이고, 안내만 뜬 채 날짜가
2020년에 머문다.

이 동작 자체는 002 **FR-010**("선택 날짜가 조회 가능 범위를 벗어나면 시스템은 조회 가능한
범위를 알리고 값을 반환하지 않아야 한다")을 따른다. 데이터가 정상이면 오늘은 범위 안이거나
하루 밖이라 이 경로를 타지 않는다.

**다만 UX 결함이 하나 있다.** FR-010은 "값을 반환하지 않는다"만 말하고 **선택 자체를
거절하라고는 하지 않았다.** 현재 구현은 안내를 띄우면서 날짜 입력은 이전 값으로 되돌려,
사용자가 보기에 **클릭이 먹지 않은 것처럼** 보인다. 입력값과 안내가 서로 다른 이야기를 한다.

### #3 — 진짜 UI 결함

`frontend/src/components/fx/CurrencyTabs.tsx`의 활성 탭이 **배경과 같은 색**이다.

```tsx
<div className="inline-flex rounded-lg border border-gray-300">   // 배경 없음
  active ? "bg-white font-semibold text-gray-900 shadow-sm" : "text-gray-500"
```

컨테이너에 배경이 없어 페이지 배경(흰색)이 그대로 비친다. 활성 탭의 `bg-white`가 **흰색 위
흰색**이 되어, 구별되는 것은 글자 굵기와 옅은 그림자뿐이다.

분절 컨트롤(segmented control)의 표준 형태는 **컨테이너가 회색, 활성 항목이 흰색**이다.
이 코드는 후자만 가져오고 전자를 빠뜨렸다.

**002 다크 모드 수정과 무관하다.** 002 구현 시점부터 있던 결함이며, 라이트 모드에서도
같은 증상이 난다.

## 심각도

| 항목 | 심각도 | 근거 |
|------|:------:|------|
| #1 | **HIGH (환경)** | 코드 결함은 아니나, 개발 DB가 언제든 다시 날아간다. 재발 방지가 필요하다 |
| #2 | **LOW** | FR-010을 따르고 있다. 입력값과 안내의 불일치만 손보면 된다 |
| #3 | **MEDIUM** | 선택 상태가 보이지 않아 사용자가 어느 통화를 보는지 알 수 없다 |

## Proposed Remediation

### R1 — 테스트 DB 분리 (#1 재발 방지)

통합 테스트가 **별도 데이터베이스**를 쓰게 한다. 환경변수 `DB_NAME`을 테스트에서만
덮어쓰는 방식이 가장 작다.

- `backend/tests/integration/conftest.py`의 `settings` 픽스처가 `DB_NAME`에 접미사를 붙인다
- 접미사는 설정으로 선언하고 기본값을 둔다 (헌법 원칙 II)
- 기존 `reset_schema()` 동작은 그대로 — 대상 DB만 바뀐다

이것만으로 개발 데이터가 다시 날아가는 일이 없어진다. **CLAUDE.md의 "개발 서버를 띄운 채
통합 테스트를 돌리지 말 것" 경고도 불필요해진다.**

### R2 — 범위 밖 선택 시 입력값 정합 (#2)

`selectDate`가 범위 밖이어도 **선택 날짜는 반영**하고, 값만 반환하지 않는다. FR-010의
"값을 반환하지 않는다"는 지키면서 입력값과 안내가 같은 이야기를 하게 한다.

- `selectedDate`를 요청한 날짜로 설정
- 안내는 그대로 표시
- 요약·표·차트는 값 없음 상태로

### R3 — 통화 탭 배경 (#3)

컨테이너에 옅은 배경을 주어 활성 탭이 드러나게 한다.

- `inline-flex rounded-lg border border-gray-300` → `bg-gray-100` 추가
- 활성 탭의 `bg-white shadow-sm`이 그 위에서 떠 보인다
- 비활성 글자색도 대비를 확보한다

### 실제 데이터 복구 (#1 즉시 조치)

R1과 별개로, 현재 오염된 데이터를 실제 수집분으로 채워야 한다. 사용자가 화면에서 수집을
시작하면 된다. **오늘 ECOS 호출을 얼마나 썼는지 확인 후 진행한다.**

## Risks & Considerations

- **R1은 테스트 인프라를 건드린다.** DB 이름이 바뀌면 첫 실행 시 마이그레이션이 새로
  돌아야 한다. 기존 테스트가 전부 통과하는지 확인이 필요하다.
- **R2는 002의 FR-010 해석을 바꾼다.** "값을 반환하지 않는다"와 "선택을 거절한다"를 분리하는
  것이 명세 의도에 맞는지 판단이 필요하다. 명세 변경까지 갈 사안은 아니라고 본다 —
  FR-010은 선택 거절을 요구하지 않았다.
- **R3은 002 화면과 003 수집 화면 양쪽에 영향**한다. `CurrencyTabs`를 두 화면이 공유한다.
- **#1의 데이터 복구는 ECOS 일일 한도를 쓴다.** 전체 백필이 통화당 약 146회이고 실측 하한이
  150회다. 하루에 한 통화만 하는 것이 안전하다.
