# Research: 가상자산 투자 시뮬레이션

**Feature**: `007-crypto-investment-simulation` | **Date**: 2026-10-03 | **Spec**: [spec.md](./spec.md)

출처(investing.com)는 2026-10-03에 이 저장소의 개발 기기에서 실측했다. 요청은 목록 74건(영문·한국어 판 각 37쪽), 일봉 10여 건,
페이지 몇 건이며 요청 사이를 1~1.5초 띄웠다. 수치는 그날의 값이다.

---

## R7-1. 출처 접근 — 무엇이 막히고 무엇이 통하는가 (FR-016, FR-018, FR-020)

**측정**:

| 클라이언트 | 페이지(`www`·`kr`) | 목록 API | 일봉 API |
|------------|--------------------|----------|----------|
| curl, Chrome 사용자 에이전트 | 403 (본문 `403`) | 403 | 403 |
| 헤드리스 Chrome, 기본 사용자 에이전트(`HeadlessChrome/…`) | 403 | — | — |
| 헤드리스 Chrome, 일반 Chrome 사용자 에이전트 | 200 | 200 | 200 |
| **aiohttp, 기본 사용자 에이전트** | — | 403 | 403 |
| **aiohttp, Chrome 사용자 에이전트** | — | **200** | 403(HTML 확인 페이지) |
| **aiohttp, Chrome 사용자 에이전트 + `domain-id: www`** | — | **200** | **200** |

응답은 Cloudflare를 거친다(`server: cloudflare`, `cf-ray`). 로그인·쿠키·토큰은 필요 없다.

**Decision**: 백엔드가 **aiohttp로 직접** 받는다. 사용자 에이전트(브라우저형 문자열)와 `domain-id` 헤더는 **설정**으로 둔다(헌법 원칙 II —
인증·정책은 설정). 브라우저(헤드리스 Chrome)는 쓰지 않는다 — 운영 기기에 Chrome이 필요해지고(크로스 플랫폼 제약), 필요 없다는 것이
측정으로 드러났다.

- **403은 "차단"이다**(재시도로 풀리지 않는다). 본문이 `403`이거나 HTML 확인 페이지면 `blocked`로 분류해 사유와 함께 실패한다(FR-020).
  자동 재시도는 하지 않고, 다음 실행이 다시 시도한다
- 429·5xx·연결 오류는 지수 백오프 + 지터로 재시도한다(헌법 원칙 II). 횟수·간격은 설정
- 동시 호출 1, 요청 사이 최소 1.5초(설정). 목록 74건을 1초 간격으로 받아도 막히지 않았다 — 공개된 한도는 없다

**Alternatives considered**: 헤드리스 Chrome으로 페이지 안에서 호출 — 통하지만 Chrome 설치가 필요하고 aiohttp로 충분하다. TLS 지문을
흉내 내는 클라이언트(curl_cffi 등) — 의존성이 늘고 원칙 I(aiohttp)과 어긋난다. 페이지 HTML 파싱 — 목록·일봉 모두 JSON API가 있어
불필요하다.

**위험**: 출처가 차단 기준을 바꾸면 수집이 막힌다(자동 접근 차단은 정상 경로로 다룬다 — FR-018 실패 양상). 사용자 에이전트를 설정으로 둔
이유다.

## R7-2. 이용약관 (FR-018, 헌법 원칙 II)

**측정**: 사이트 모든 페이지 아래의 고지 —

> It is prohibited to use, store, reproduce, display, modify, transmit or distribute the data contained in this website without
> the explicit prior written permission of Fusion Media and/or the data provider.

이용약관 페이지(`/about-us/terms-and-conditions`)는 자동 조작으로 본문이 렌더링되지 않았다. `robots.txt`는 `/crypto/`·API 경로를
막지 않는다(`/login`·`/members` 등만 막는다).

**Decision**: 약관은 **허가 없는 저장·사용을 금지한다.** 사용자 결정(2026-10-03, spec Clarifications)대로 **개인 이용을 전제로 그대로
자동 수집하고 원칙 II 이탈로 기록한다**(plan Complexity Tracking). 005의 Yahoo 비공식 엔드포인트와 같은 잠정 결정이다 — 받은 데이터를
재배포하지 않고 저장소는 비공개다. 도구를 공개하거나 여러 사용자에게 제공하면 출처를 다시 정한다.

쓰는 엔드포인트는 **공개 API가 아니다**(사이트 화면이 쓰는 내부 API). 문서·버전 보장이 없어 형식이 바뀔 수 있다 — 계약 테스트의 픽스처가
그 시점의 형식을 고정한다.

## R7-3. 일봉 — 엔드포인트, 형식, 기준 시각 (FR-010~FR-013, FR-021, FR-022)

**측정**: 과거 데이터 화면(`/crypto/bitcoin/historical-data`)이 부르는 API —

```
GET https://api.investing.com/api/financialdata/historical/{instrument_id}
    ?start-date=YYYY-MM-DD&end-date=YYYY-MM-DD&time-frame=Daily&add-missing-rows=false
헤더: User-Agent(브라우저형), domain-id: www   (domain-id가 없으면 400 "Domain required")
→ {"data": [행…], "summary": {…}}
```

행(최신순):

```json
{"rowDate": "Oct 02, 2026", "rowDateRaw": 1790899200, "rowDateTimestamp": "2026-10-02T00:00:00Z",
 "last_open": "84,813.4", "last_openRaw": "84813.35937500000000",
 "last_max": "87,128.6", "last_maxRaw": "87128.63281250000000",
 "last_min": "83,894.3", "last_minRaw": "83894.25781250000000",
 "last_close": "84,515.5", "last_closeRaw": "84515.53125000000000",
 "volume": "86.35K", "volumeRaw": 86349, "change_precent": "-0.43", "change_precentRaw": -0.4295…}
```

- **기준 시각은 UTC 하루다.** `rowDateTimestamp`가 모두 `T00:00:00Z`이고, 2026-10-03 일봉 시가(84512.8816753)가 차트 API의 **10-03 00:00Z
  시간봉 시가와 같고**, 10-02 일봉 종가가 **10-02 23:00Z 시간봉 종가와 같다.** 헌법 원칙 V(가상자산 일봉 UTC 00:00)와 맞는다
- **오늘(UTC) 일봉이 마감 전에도 온다**(10-03 09:39Z에 10-03 행이 있었다). → 잠정
- **한 번에 최대 약 5,000행**이다. BTC를 2010-01-01 ~ 2026-10-03으로 요청하면 **오래된 쪽부터** 4,999행(2010-07-18 ~ 2024-03-24)에서
  잘렸다. 잘렸다는 표시는 없다
- **화면용 문자열은 코인의 자릿수로 반올림되어 정보를 잃는다** — 2010-07-18 BTC 시가 `last_open: "0.0"`, `last_openRaw:
  "0.04950999841094"`. 원값(`…Raw`)은 **소수 14자리 문자열**이다(SHIB `0.00000579000016`). 원값은 출처가 단정밀도로 보관한 값을
  십진수로 옮긴 것이라 끝자리에 흔적이 있다(`84587.0859375` = float32로 정확히 표현되는 값)
- 거래량: `volumeRaw`는 정수, `volume`은 `K`/`M`/`B` 접미사 문자열. **값이 없는 날은 `volume: ""`·`volumeRaw: 0`**으로 온다(BTC
  2011-06-20 ~ 06-25, Mt.Gox 중단 기간 6일)
- 빠진 날: BTC 2010-07-18 ~ 2024-03-24 4,999행에 **빠진 날 0일**. ETH 2016-03-10 ~ 2026-10-03 3,860행
- 첫 일봉: BTC 2010-07-18, ETH 2016-03-10(출처 기준)
- **목록에 있어도 일봉이 없는 코인이 있다** — Doge Killer(LEASH)는 0행

**Decision**:

1. 일봉 = UTC 날짜 하나. 날짜는 `rowDateTimestamp`의 날짜 부분으로 읽는다(`rowDate` 문자열은 쓰지 않는다)
2. 가격은 **원값(`…Raw`) 문자열을 그대로 `Decimal`로** 읽는다 — `float`를 거치지 않고, 반올림하지 않는다(헌법 원칙 V·VI, 006 R6-18과 같은
   태도). 화면용 문자열은 쓰지 않는다 — 반올림으로 작은 값이 `0.0`이 된다
3. 거래량은 `volumeRaw`를 쓰되, **`volume`이 빈 값·`-`이면 `NULL`**이다(FR-012a — 0으로 만들지 않는다). **가격 원값이 빠지거나 숫자가
   아닌 행이 하나라도 있으면 그 청크 전체를 형식 오류로 실패시킨다** — 받은 행을 저장하지 않고 커버리지를 기록하지 않으며, 사유(날짜·필드)를
   작업 기록과 수집 로그에 남긴다. 다음 실행이 그 청크를 다시 받는다. 그 행만 버리면 그날이 출처 결측(R7-9)으로 보여, 형식 문제가 데이터
   공백으로 위장된다(analyze M2)
4. **계산 끝 = 마지막으로 마감된 UTC 하루(UTC 오늘 − 1일).** 정규화할 때 그 날짜보다 뒤의 행(오늘·미래)은 **버린다** — 잠정 일봉을
   저장하지 않으므로 확정값과 섞일 일이 없다(FR-022). 원본에는 그대로 남는다(헌법 원칙 V — 원본 보존)
5. **청크는 730일**(주식과 같다, `CHUNK_DAYS`). 5,000행 상한 아래라 잘림이 없다. 응답 행 수가 상한 근처(4,900행 이상)면 형식 오류로 다룬다
   — 조용히 잘린 구간을 받은 것으로 기록하지 않는다
6. 수집 구간: 시작 월 1일 ~ 계산 끝. 커버리지에는 **요청한 구간**을 기록한다(받으러 갔는데 일봉이 없던 구간도 다시 받지 않게 — 005와 같다)

**Alternatives considered**: 화면의 Download(CSV) — 로그인이 필요한지 확인하지 않았고, 같은 데이터를 API가 원값 정밀도로 준다. 잠정
일봉을 `is_provisional`로 저장 — 계산에 쓰지 않는 값을 저장할 이유가 없다(YAGNI). 다음 수집이 확정값으로 덮는 흐름도 필요 없다.

## R7-4. 코인 목록 — 엔드포인트, 규모, 식별자 (FR-003~FR-006, FR-005a)

**측정**: 목록 화면(`/crypto/currencies`)이 부르는 API —

```
GET https://endpoints.investing.com/pd-instruments/v1/crypto/coins
    ?sort=rank&order=asc&limit=100&domain_id={1|18}[&cursor=…]
헤더: User-Agent(브라우저형)
→ {"coins": [코인…], "next_page_cursor": "…" | null}
```

- `limit` 상한 100("number must be at most 100", 400). 커서로 쪽을 넘긴다(커서는 `{"s":"rank","o":"asc","p":100}`의 base64)
- **전체 3,654개, 37쪽**(영문 판). 한국어 판도 3,654개
- 코인 필드: `instrument_id`(일봉 API의 식별자), `cmc_id`, `slug`, `symbol`, `name`, `rank`, `price`, `price_decimal_places`, `market_cap`,
  `url`(4개는 빈 값), `last_updated` 등
- **`instrument_id`는 빈 값 0, 중복 0**이다. `slug`·`cmc_id`도 유일하다. **`symbol`은 169개가 겹친다**(MAX 5개, AI·ONE 4개 …), `name`은
  4개가 겹친다
- 가격 범위: 2e-12(Doge Killer) ~ 10만 달러대
- 한국어 판(`domain_id=18`)은 **같은 `instrument_id`로 3,654개 모두 짝지어진다**

**Decision**:

1. 코인의 식별 = **(출처, `instrument_id`)**. 일봉 API가 이 값을 그대로 받으므로 따로 변환할 것이 없다(FR-004). `slug`는 표시·이력 보조
2. 한글 이름 = 한국어 판의 `name`이 **영문 판과 다르고 한글을 포함할 때만**(FR-006). 짝짓기는 `instrument_id`로만 한다 — 이름·심볼로 짝짓지
   않는다
3. 한 번 갱신 = 영문 37쪽 + 한국어 37쪽 = 74요청(1.5초 간격이면 약 2분). **일주일에 한 번**(FR-005), 실패하면 다음 날 첫 검색 때
4. 교체는 **두 판을 모두 받은 뒤 한 트랜잭션**으로(006 R6-4와 같다). 이전보다 50% 넘게 줄면 거절한다(출처가 일부만 준 경우). 한국어 판만
   실패하면 영문 판으로 교체하고 한글 이름은 이전 값을 둔다(FR-006 — 영문으로는 계속 찾는다)
5. 목록에서 빠진 코인은 지우지 않고 `missing`(FR-005a)
6. 원본은 쪽마다, 같은 본문은 한 번만 보관한다(006 R6-13과 같다)
7. **시세 통화는 USD**다. 목록 API에 `currency_id`를 넘기지 않으면 USD 가격이고, 일봉 API도 USD다. 코인마다 다르지 않다

## R7-5. 한글 이름의 범위 — 측정 결과가 명세의 기대보다 작다 (FR-006, SC-002)

**측정**: 한국어 판의 이름이 한글인 코인은 **3,654개 중 12개**다 — 비트코인, 이더리움, 테더, 솔라나, 도지코인, 카르다노, 라이트코인,
시바이누, 이더리움 클래식, 대시, 시아코인, 비트쉐어. **상위 50개 중 8개**다. XRP·BNB·TRON 등은 한국어 판에서도 영문 그대로다.

**Decision(지금)**: 명세 그대로 한국어 판의 한글 이름만 쓴다. 12개는 한글·초성으로 찾히고 나머지는 영문 이름·심볼로 찾힌다. SC-002 둘째
문장("한글 이름이 있는 코인을 한글·초성으로 찾으면 95%")은 만족할 수 있다.

**사용자 결정(2026-10-03): 지금대로 진행한다** — 한국어 판의 한글 이름만 쓰고, 다른 출처로 넓히지 않는다. 아래는 그 판단의 근거로 남긴다.

**검토한 확장**: 한글 검색의 실효 범위가 사용자의 기대("주식처럼 한글로 찾는다")보다 작다. 넓히려면 **한글 이름의 다른 출처**가
필요하다 — 예: 국내 거래소의 공개 마켓 목록(한글·영문 이름과 심볼). 다만 그 목록과 investing의 코인을 **심볼로** 짝지어야 하는데 심볼이
169개 겹쳐(R7-4) FR-006의 실패 양상(다른 코인의 시세로 계산)에 정면으로 걸린다. 짝짓기 규칙(심볼이 양쪽에서 유일할 때만 등)과 출처
약관을 따로 정해야 한다. 넓히려면 별도 기능으로 다룬다.

## R7-6. 검색 — 006의 색인을 그대로 쓴다 (FR-003, FR-004, FR-006, SC-002)

**Decision**: `src/search/match.py`의 `SearchIndex`를 그대로 쓴다 — `SearchEntry(key=코인 id, names=(한글 이름, 영문 이름),
codes=(심볼,), market="CRYPTO", code=심볼)`. 한글·초성·받침 대기 규칙이 주식과 같다(spec Assumptions). 색인은 006처럼 메모리에 두고
목록 갱신 기록의 기준 시각을 버전으로 삼는다(006 R6-5).

**같은 순위의 정렬에 시가총액 순위를 쓴다.** 지금 `SearchIndex`는 같은 일치 종류 안에서 "이름이 짧은 순 → 가나다·알파벳 → 시장 → 코드"다.
심볼이 겹치는 코인(MAX 5개)이 이름 길이로 정렬되면 시가총액이 작은 코인이 위에 온다. `SearchEntry`에 **선택 항목 `priority`(작을수록
위, 기본 0)**를 더해 일치 종류 바로 다음 기준으로 쓴다. 주식은 0을 넣으므로 006의 순서가 바뀌지 않는다(회귀는 006 검색 테스트가 지킨다).

**Alternatives considered**: 코인 전용 색인 — 한글 규칙을 두 벌 두게 된다. DB `LIKE` — 초성 일치를 표현할 수 없다(006 R6-5).

## R7-7. 시뮬레이션 — 순수 함수, 소수 수량 (FR-025~FR-031)

**Decision**: `src/simulation/crypto_hold.py`를 새로 둔다(DB·HTTP 없음, 헌법 원칙 IV). 주식의 `reinvest.py`를 일반화하지 않는다 — 배당·
분할·재투자·정수 수량이 모두 빠져 공유할 것이 계산 뼈대뿐이고, 일반화하면 주식의 참조 구현 대조가 흔들린다(YAGNI).

- 입력: 일봉 시가 목록(날짜·시가), 조건(시작일, 원금(시세 통화), 수수료율)
- 매수: 시작 월의 **첫 일봉**(1일이 결측이면 그 달의 첫 일봉, FR-030) 시가로 1회. 수량 = ⌊예수금 ÷ (시가 × (1 + 수수료율))⌋₈(소수 8자리
  버림). 수수료 = 수량 × 시가 × 수수료율. 예수금 = 원금 − 수량 × 시가 − 수수료. **총액이 예수금을 넘지 않는다**(버림이라 성립한다 —
  테스트로 고정, SC-004)
- 행: 매달의 첫 일봉(1일, 결측이면 그 달의 첫 일봉), 최신순. `latest` = 마지막 일봉(보드용, 005와 같다)
- `src/simulation/money.py`에 소수 수량 함수(`buy_fraction`)를 더한다 — 정수 수량 함수(`buy_quantity`)는 그대로 둔다

**참조값 테스트**(헌법 원칙 VI): 외부 참조 구현이 없다. 손으로 계산한 사례를 **계산 과정과 함께** 테스트에 적어 기대값의 근거를 남긴다. 예: 시가
7,196.39111328125(BTC 2020-01-01), 원금 10,000달러, 수수료 0.1% → 10,000 ÷ (7,196.39111328125 × 1.001) = 1.388197…를 8자리에서 버려
수량 **1.38819719**, 수수료 **9.9900099215980029296875**, 쓴 돈 9,999.9999315…, 예수금 **0.0000684803990673828125**.

## R7-8. KRW 평가와 환전 — 006의 규칙을 공용 함수로 (FR-034~FR-036)

**Decision**: 006(T142)이 `stock_simulation._evaluate` 안에 둔 KRW 평가식(투자 수익 = (잔고 + 예수금) × 그 행의 매매기준율 − KRW 원금,
수익율 = 투자 수익 ÷ KRW 원금, 잔고 KRW)을 **순수 함수 하나**(`simulation/fx_convert.py`의 `evaluate_krw`)로 옮기고 주식·가상자산이 함께
쓴다. 같은 규칙을 두 곳에 두면 한쪽만 고쳐질 때 이력 비교의 기준이 갈라진다(006 FR-068의 실패 양상).

- 환전(현금 살 때 + 우대)·환율 읽기(`load_rates`·`build_exchange`·`cash_buy_spread`)는 006의 `api/services/stock_fx.py`를 그대로 쓴다
- `fx_currency_for(stock)`를 **통화 문자열을 받게** 바꾼다(`fx_currency_for(currency)`) — 주식과 가상자산이 함께 쓴다
- 환율 판정(`plan_fx`·`require_fx_available`)은 006의 `stock_collect`에 이미 통화 단위로 있다 — 그대로 부른다
- 시세 통화가 USD로 고정이라(R7-4) 원금 통화는 KRW 또는 USD다
- **평가와 환전에는 확정 환율만 쓴다**(analyze C1) — `load_rates`가 `series(…, confirmed_only=True)`로 읽는다. 잠정 환율만 있는 날은 지금의
  `resolve_rate`가 가장 가까운 이전 확정 고시일을 쓰고 그 날짜를 돌려주므로(006 FR-041c), 화면의 "다른 날짜의 환율을 썼다" 표시가 그대로
  드러낸다. 헌법 원칙 V("잠정값을 시뮬레이션 입력으로 쓰면 결과에도 드러나야 한다")를 지키는 가장 작은 변경이다. **005·006부터 있던
  빈틈**이다 — 그때 `load_rates`는 잠정 행까지 읽었다. 주식 결과는 "날짜가 지났는데 아직 잠정인 환율"이 계산 구간에 있을 때만 바뀐다(계산
  끝이 어제라 오늘의 잠정 환율은 원래 들어오지 않는다). 잠정 표시를 결과에 싣는 대안은 화면 요소와 응답 필드가 늘어 택하지 않았다

주식 경로를 건드리므로 006의 테스트 전체가 회귀 검사다(plan Complexity Tracking).

## R7-9. 결측 — 휴장과 다른 이유 (FR-023, FR-043, SC-005)

**Decision**: `api/services/series_query.compute_gaps`에 **커버리지 안 빈 날의 사유**를 매개변수로 둔다 — 외환·주식은 지금처럼
`no_quote`(휴장, 잇는다), 가상자산은 `source_missing`(출처 결측, **끊는다**). 프론트엔드 `splitSeriesAtGaps`는 `source_missing`도 끊고, 범례에
"결측 N구간"을 보인다.

표는 월 행만이라 결측일을 직접 보이지 않는다. 월 1일이 결측이면 그 달의 첫 일봉이 그 달의 행이고, **그 행에 "1일 결측 — N일 일봉"을
표시**한다(FR-030). 매수일이 1일이 아니면 보드·표에 그 날짜가 보인다.

**Alternatives considered**: 결측일을 표의 행으로 넣기 — 월 행 규칙(FR-038)과 섞인다. 휴장으로 다루기 — FR-023의 실패 양상 그대로다.

## R7-10. 시작 가능 날짜 — 수집 중 발견 (FR-008, FR-009)

목록 API에는 상장일·첫 거래일이 없다(R7-4 필드). 일봉 API는 요청 구간의 앞부분이 비어 있으면 그냥 늦은 날부터 준다(R7-3).

**Decision**: **수집이 끝날 때** 그 코인의 커버리지 시작(`covered_from`)보다 첫 일봉이 늦으면 그 첫 일봉 날짜를 `first_available_date`로
기록한다 — 출처가 그 앞에는 일봉이 없다는 확실한 근거다(006 R6-8의 `price_start`와 같다). 판정은 둘이다 —

- **수집 전**: 기록된 `first_available_date`보다 이른 시작일은 400(`before_listing`, `basis: price_start`)과 그 날짜. 수집하지 않는다
- **수집 후**: 시작 월에 일봉이 하나도 없으면 같은 400(006 R6-8)

기준 시작일 2010-01-01은 상수가 아니다 — 시작일 하한을 코드에 두지 않는다(헌법). 2010년 이전 시작은 빈 청크 몇 개를 받아 보고 위 규칙으로
막힌다.

일봉이 아예 없는 코인(Doge Killer)은 수집이 끝나도 일봉이 없어 "출처에 시세가 없다"로 답한다(005 FR-004와 같다).

## R7-11. 수집 실행 — 주식과 같은 구조, 별도 줄 (FR-013~FR-015, FR-019)

**Decision**: 005·006의 주식 구조를 그대로 본뜬다 — `worker/crypto_queue.py`(시작 큐), `worker/crypto_runner.py`(청크 수집),
`worker/crypto_worker.py`(앱 수명 태스크), DB 점유(`crypto_collection_lock`), 작업 기록(`crypto_collection_job`), 진행 SSE
(`/api/crypto/progress`, 받은 날 / 받을 날, 006 FR-045a·R6-19의 `no-transform`·프레임마다 rollback).

- **목록 갱신은 별도 줄**(`worker/crypto_list_worker.py`) — 74요청(약 2분)이 끝날 때까지 시세 수집이 **멈추지 않게** 한다. 두 줄은
  **같은 출처**라 `InvestingClient` 하나의 간격 제한기(세마포어 + 최소 간격)를 함께 쓴다 — 출처 입장에서는 한 클라이언트다. 그래서 갱신하는
  동안 시세 수집은 **느려진다**(요청이 번갈아 나간다)
- **목록 갱신의 진행을 SSE로 흘린다**(FR-005b, 헌법 원칙 VII, analyze C2) — `GET /api/crypto/list/progress`. 갱신 줄이 쪽을 받을 때마다 점유
  행(`crypto_list_lock`)에 판·받은 쪽 수·받은 코인 수를 적고, 스트림이 프레임마다 그 행과 갱신 기록을 새로 읽는다(006 R6-19 — 프레임마다
  rollback). 전체 쪽 수는 이전 갱신의 코인 수 ÷ 100으로 어림하고, 처음이면 없다. 검색 칸은 목록 상태가 `never`·`refreshing`일 때 구독한다
- `lifespan`이 띄우는 태스크가 4개 → 6개가 된다(가상자산 수집, 목록 갱신). 단일 워커(`--workers 1`) 전제는 그대로다(CLAUDE.md)
- 수집 사건(시작·청크·완료·실패·차단)과 목록 갱신 사건은 `logs/collection.log`에(006 FR-065와 같다)
- 기동 시 고아 점유 회수는 주식과 같은 방식(`reconcile`)으로 가상자산 점유도 본다

**006의 교훈**(006 plan Complexity Tracking D1): 워커 등록·`lifespan`·목록 갱신 요청처럼 **다른 경로가 대신 불러 주지 않는 실행 주체**는
그 주체를 거쳐야만 통과하는 테스트와 짝지어 둔다.

## R7-13. 저장 정밀도 (FR-031, 헌법 원칙 VI)

**Decision**: 가상자산 가격 열은 `DECIMAL(36, 14)` — 원값이 소수 14자리로 오고(R7-3), 정수부 22자리까지 담는다. 주식의
`PRICE`(`DECIMAL(20, 6)`)는 2e-12 같은 가격을 0으로 만든다. 거래량은 `DECIMAL(38, 8)`(SHIB 하루 2.6조 개). 수수료율은 기존
`SPREAD`(`DECIMAL(9, 6)`). 계산 중 수량은 `Decimal` 소수 8자리, 금액은 통화 자릿수(USD 2·KRW 0)로 표시하되 계산은 자르지 않는다(005와 같다).

## R7-14. 보드 통화 기호 위치와 차트 축 쉼표 (FR-042a, FR-043a) — 반복 2026-10-04

**Decision**:

- 성과 보드의 투자 원금·투자 수익(원금 괄호의 KRW 포함)은 기호를 **숫자 앞**에 둔다 — `₩10,000,000`, `$1,000.50`, `¥100,000`. 손실은 부호 →
  기호 → 숫자(`-₩5,446`). 기호를 모르는 통화는 통화 코드와 공백(`GBP 1,000`). `formatMoneyWithSymbol` 하나만 바꾸고 `formatMoney`는 그대로다
- 성과 추이 차트의 두 축은 **시리즈마다** `priceFormat: { type: "custom", minMove, formatter }`로 형식을 준다. 잔고 축은 `basisCurrency`(KRW)라
  소수점 없이(`minMove: 1`, `360,000,000`), 수익률 축은 소수 2자리(`minMove: 0.01`, `3,200.00`). 쉼표는 `formatAxisNumber(value, digits)`가
  넣는다 — 축 눈금 전용이고 그리기용 숫자를 받는다

**Rationale**:

- 사용자 요청(2026-10-04). 006 R6-21은 "기호를 숫자 앞에(`$1,000`)"를 사용자 예시가 뒤라는 이유로 기각했다. 그 근거를 사용자가 바꿨으므로
  이번에 채택한다. 보드는 주식 화면(005·006)과 같은 컴포넌트라 두 화면이 함께 바뀐다 — 006 FR-054를 대체한다
- 부호를 기호 앞에 두는 것은 006과 같은 이유다 — `₩-5,446`은 손실 표시가 숫자 가운데 묻힌다
- 축 형식은 시리즈 옵션이고, 이 차트는 결측으로 끊긴 구간마다 시리즈를 새로 만든다(005 FR-034). 가격 축은 그 축에 붙은 시리즈 하나의 형식을
  따르므로 **모든 구간에** 줘야 한다 — 첫 구간에만 주면 어느 시리즈를 따르느냐에 따라 쉼표가 빠지고 오류는 나지 않는다
- 잔고 축의 소수점은 사용자 결정이다(define 2026-10-04) — 보드·표의 원화 표시(`formatMoney`, KRW·JPY 소수점 없음)와 같은 규칙
- 차트 값은 이미 그리기용 `Number`다(`toPerformanceData`). 축 문자열은 그 값의 표시일 뿐이고 값의 진실은 툴팁·표의 원본 문자열이다(헌법 원칙 VI)

**Alternatives considered**:

- 차트 전체의 `localization.priceFormatter` — 두 축이 한 함수를 써서 잔고 0자리·수익률 2자리를 나눌 수 없다
- `Number.prototype.toLocaleString()` — 실행 환경 로캘에 따라 구분자가 바뀐다(`360.000.000`). 테스트와 브라우저가 다를 수 있다
- 잔고 축 `.00` 유지 — 원화에 없는 소수점(사용자가 기각)

**반복 2026-10-04 #2 — 이력 비교 차트 (FR-046a, SC-016)**:

- Decision: 축 형식 객체를 `lib/chartSeries.ts`의 `axisPriceFormat(fractionDigits)`로 옮겨 성과 추이 차트와 이력 비교 차트가 함께 쓴다.
  비교 차트의 수익률 축은 소수 2자리(`1,881.47`)
- Rationale: 결측 규칙을 `splitSeriesAtGaps` 하나로 두어 차트마다 갈리지 않게 한 것과 같은 이유 — 형식을 두 곳에 두면 한쪽만 고쳐져
  같은 화면의 두 수익률 축이 다른 형식으로 보인다. 비교 차트도 이력 항목마다, 결측으로 끊긴 구간마다 시리즈가 따로라 모든 시리즈에 준다
- Alternatives considered: `ComparisonChart` 안에 같은 객체를 한 번 더 쓴다(두 벌 — 기각)

**범위 밖**: 보드·표·툴팁의 수익률(`+1881.47%`). 같은 문제가 있으나 요청이 아니다. 표의 수익률에 쉼표를 넣으면 열 폭이 늘어 1440px
맞춤(SC-010)을 다시 확인해야 한다. 이력 비교 차트의 수익률 축은 반복 #2에서 넣었다(FR-046a).
