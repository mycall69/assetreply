# Data Model: 외환 수집 실행 계층과 실시간 관측 화면

**Feature**: 003-fx-collection-runtime | **Date**: 2026-09-24

001·002의 7개 테이블을 그대로 쓴다. 이 문서는 **변경분과 신규분만** 다룬다. 변경되지 않은
테이블의 정의는 [001 data-model.md](../001-fx-rate-history/data-model.md)와
[002 data-model.md](../002-fx-analysis-workspace/data-model.md)를 참조한다.

스키마 변경은 Alembic 리비전으로만 관리한다(헌법 DB 운영 규약). 수동 DDL은 금지한다.

---

## 1. `fx_collection_event` — 수집 이벤트 [신규]

이번 기능이 추가하는 **유일한 신규 테이블**이다.

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| `id` | `BIGINT` | PK, AUTO_INCREMENT | |
| `job_id` | `BIGINT` | NOT NULL, FK → `fx_collection_job.id` | 어느 실행 시도에 속한 사건인가 |
| `currency_code` | `CHAR(3)` | NOT NULL, FK → `currency.code` | 통화별 조회·정리의 기준 |
| `kind` | `VARCHAR(30)` | NOT NULL | 사건 종류 (아래 표) |
| `chunk_from` | `DATE` | NULL 허용 | 구간 요청 범위 시작 |
| `chunk_to` | `DATE` | NULL 허용 | 구간 요청 범위 끝 |
| `rows_stored` | `INT` | NULL 허용 | 저장된 데이터 건수 |
| `detail` | `TEXT` | NULL 허용 | 사람이 읽는 설명. 오류 사유가 들어간다 |
| `occurred_at` | `TIMESTAMP` | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 발생 시각 |

`currency_code`를 `job_id`와 함께 두는 것은 비정규화다. 작업을 거쳐 조인하면 얻을 수 있지만,
**정리(FR-023)와 조회가 모두 통화별로 일어나기 때문에** 매번 조인하게 된다.

### 인덱스

| 인덱스 | 목적 |
|--------|------|
| `(job_id, occurred_at)` | 작업별 시간순 조회 |
| `(currency_code, job_id)` | 통화별 보관 범위 정리 (R3-9) |

### 사건 종류 (`kind`)

| 값 | 의미 | 필수 필드 |
|----|------|-----------|
| `job_started` | 작업 시작 | — |
| `chunk_requested` | 구간 요청 | `chunk_from`, `chunk_to` |
| `chunk_stored` | 구간 저장 완료 | `chunk_from`, `chunk_to`, `rows_stored` |
| `chunk_empty` | 출처가 값을 제공하지 않음 (휴일 등) | `chunk_from`, `chunk_to` |
| `chunk_failed` | 구간 수집 실패 | `chunk_from`, `chunk_to`, `detail` |
| `retry` | 재시도 발생 | `chunk_from`, `chunk_to`, `detail` |
| `rate_limited` | 호출 한도 신호 | `detail` |
| `job_finished` | 작업 종료 | `detail`(종료 사유) |
| `log_sink_failed` | 파일 기록 실패 (R3-4) | `detail` |

**`chunk_empty`와 `chunk_failed`를 나누는 것이 이 표의 핵심이다.** 명세의 Edge Case가 요구하는
구별이며, 둘을 한 종류로 묶으면 나중에 시계열에 공백이 생겼을 때 출처의 결측인지 수집 실패인지
알 수 없다(FR-021).

### 보관 규칙

통화별 최근 20개 작업에 속한 사건만 남긴다. 작업이 끝날 때 그 통화의 21번째 이후 작업에 속한
사건을 지운다(FR-023, R3-9).

**작업 행 자체는 지우지 않는다.** 사건만 정리 대상이다. 작업 목록은 가볍고, 지우면 "언제
수집했는지"가 사라진다.

## 2. `fx_collection_job` — 기록 불완전 표시 추가

### 추가 컬럼

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| `events_dropped` | `INT` | NOT NULL, DEFAULT `0` | 이 작업에서 DB 적재에 실패한 사건 수 |

기존 컬럼(`range_start`, `range_end`, `status`, `chunks_total`, `chunks_done`, `started_at`,
`finished_at`, `last_error`)은 변경하지 않는다.

**왜 필요한가**: FR-018b가 "기록이 불완전하다는 사실"을 드러내라고 요구한다. DB 적재가 실패한
사건은 DB에 남길 수 없으므로(순환), 누락 **건수**를 작업 행에 남긴다. 0보다 크면 화면이 그
작업의 기록에 구멍이 있음을 표시한다(R3-4).

메모리에서 세다가 작업 종료 시 한 번 쓴다. 사건마다 갱신하면 실패가 잦을 때 그 갱신 자체가
부하가 된다.

### 상태 전이 — 이번 기능에서 비로소 실제로 일어난다

```text
        (없음)
           │ 사용자가 수집 시작
           ▼
        running ─────────────┬──────────────┬─────────────────┐
           │                 │              │                 │
           │ 모든 청크 성공   │ 일부 성공    │ 한도 소진        │ 프로세스 종료
           ▼                 ▼              ▼                 ▼
       succeeded          partial        partial           partial
                                      (사유: 한도)      (사유: 비정상/정상 종료)
```

**전이 규칙**

- `running`에서 벗어나지 못한 채 남는 작업이 있어서는 안 된다(FR-005a). 점유 회수 시점에
  `partial`로 확정한다.
- 중단 후 이어받는 실행은 **새 작업**이다(FR-005b). 기존 작업의 상태를 되돌리지 않는다.
  하나의 작업은 한 번의 실행 시도를 뜻한다.
- 한도 소진으로 중단된 작업은 `partial`이 되고 사유가 남는다(FR-025a). 사유 없이 끝나면
  나중에 기록을 봤을 때 왜 멈췄는지 알 수 없다. **한 번에 한 통화만 돌므로 중단 대상도
  하나다**(2026-09-24 반복).
- `failed`는 작업이 한 구간도 받지 못하고 끝난 경우에만 쓴다. 일부라도 받았으면 `partial`이다
  — 받은 데이터는 유효하기 때문이다.

## 3. `fx_collection_lock` — 변경 없음, 읽는 방식만 추가

컬럼은 그대로다. `heartbeat_at`을 **두 개의 서로 다른 임계값으로 읽는다**(R3-3).

| 임계 | 값 | 목적 | 근거 |
|------|-----|------|------|
| 멈춤 알림 | 60초 | 사용자에게 이상을 알린다 | FR-006 |
| 점유 회수 | 900초 (001의 기존 값) | 시스템이 점유를 되찾는다 | 001, 변경하지 않음 |

두 값이 다르다는 사실이 화면에 드러나야 한다(FR-006a). 60초가 지나면 "응답 없음", 900초가
지나면 회수되어 작업이 `partial`로 확정된다. 그 사이 구간에서 사용자가 할 수 있는 일은 없으며,
화면이 그 점을 알려야 한다.

## 4. `fx_raw_response` — 변경 없음, 호출 집계의 출처

컬럼은 그대로다. `received_at`이 오늘인 행의 수가 **오늘의 호출 수**다(R3-5).

별도 집계 테이블을 두지 않는 이유는 두 숫자가 갈라질 수 있기 때문이다. 갈라지면 어느 쪽이
맞는지 판단할 근거가 없다.

이 값은 **참고 지표**다. ECOS의 한도 리셋 시각이 비공개라 서버 날짜 기준 집계가 실제 리셋과
어긋날 수 있다. 한도 판정은 출처가 돌려주는 신호로만 하며, 이 수치로 판정하지 않는다.

### 인덱스 — 새로 만들 것이 없다

`(received_at)` 인덱스를 **001이 이미 만들어 두었다**(`FxRawResponse.__table_args__`).
오늘 호출 수 집계가 그것을 그대로 쓴다.

전체 백필이 통화당 약 146행을 남기므로 테이블이 크지 않지만, 화면이 열릴 때마다 집계하므로
인덱스가 있는 편이 낫고 이미 있다.

## 5. `fx_coverage` — 변경 없음, 시간축의 근거

커버리지가 시간축 막대의 채워진 구간이다(FR-012). 001이 정한 규칙을 그대로 쓴다.

시간축의 양 끝은 다음과 같이 정한다(R3-6).

| 끝 | 값 |
|----|-----|
| 왼쪽 | `currency.first_available_date`. 아직 발견되지 않았으면 설정의 통화별 탐색 시작일 |
| 오른쪽 | 어제 |

오른쪽 끝이 어제인 이유는 001의 규약 때문이다 — `covered_through`는 확정 수집만 반영하므로
항상 어제 이하다(002에서 확인). 오늘을 시간축에 넣으면 영원히 채워지지 않는 구간이 생긴다.

---

## 6. 이어받기 지점 — 저장하지 않음

FR-011이 요구하는 "이어받기 지점"은 진행 중 작업의 `range_start`다. 새 컬럼이 필요 없다.

작업이 어디서부터 시작했는지가 곧 이어받은 지점이기 때문이다. 001이 `next_start_date`로
계산해 `create_job`에 넘긴 값이 그대로 남아 있다.

현재 청크 구간도 저장하지 않는다. `range_start`, `chunks_done`, 청크 크기로 계산되므로
진행 이벤트에 실어 보낸다(R3-6).

## 예상 규모

| 테이블 | 예상 행 수 | 근거 |
|--------|-----------|------|
| `fx_collection_event` | 통화당 최대 약 3,000 | 전체 백필 1회가 약 146구간 × 사건 2~3개 ≈ 400행. 보관 범위 20개 작업이지만 대부분의 작업은 증분이라 사건이 적다 |
| `fx_collection_job` | 누적 증가 | 정리하지 않는다. 한 번의 실행 시도마다 1행 |
| 나머지 | 001·002와 동일 | 변화 없음 |

이번 기능은 시계열 데이터량을 늘리지 않는다. 늘어나는 것은 관측 기록뿐이며, 보관 규칙이
상한을 정한다.
