**Feature**: 001-fx-rate-history | **Date**: 2026-08-30

`research-inputs/ecos-api-notes.md`에 남긴 미확인 항목과 설계 결정이 필요한 지점을 해소한다.

## R1. ECOS 호출 한도 수치

**Decision**: 한도 수치를 코드나 설계의 전제로 삼지 않는다. 대신 세 겹으로 방어한다.

1. 청크 크기·청크 간 대기·동시 호출 수를 전부 설정값으로 둔다 (FR-005, FR-009)
2. `INFO-300`(한도 초과)을 런타임에 감지해 지수 백오프 + 지터로 대응하고, 지속되면 중단한다 (FR-007, FR-012, FR-013)
3. 어떤 한도에서도 안전하도록 기본값을 보수적으로 잡는다 (R2)

실제 수치 확인은 구현 태스크로 남긴다. 확인되면 기본 설정값만 조정하며, 코드 변경은 필요 없다.

**Rationale**: ECOS 개발명세서(`https://ecos.bok.or.kr/api/`)는 클라이언트 렌더링 SPA로,
서버가 내려주는 HTML에는 제목만 있고 한도 수치가 없다. 확인에는 브라우저 렌더링 또는 로그인이
필요하다. 검증되지 않은 숫자를 설계 전제로 넣으면 그 숫자가 틀렸을 때 재설계가 발생한다.
반면 위 3중 방어는 한도를 몰라도 성립하고, 알게 되면 설정만 조정하면 된다.

**확인된 사실**: `INFO-300` 응답 코드가 존재한다는 것은 한도가 실재하고 API가 이를 명시적으로
신호한다는 뜻이다. 기존 Apps Script는 1회 요청으로 통화당 약 8,400건을 문제없이 수신했다.

**Alternatives considered**:
- 통념상 알려진 수치(일 10,000회 등)를 전제로 설계 → 검증 불가한 수치에 의존. 기각.
- 한도 확인 전까지 구현 보류 → 한도를 몰라도 안전한 설계가 가능하므로 불필요한 차단. 기각.

**실측 결과** (2026-08-30)

| 항목 | 값 | 확인 방법 |
|------|-----|-----------|
| 1회 요청 최대 행 수 | **1000건** | 10년 요청 시 `list_total_count` 2468 대비 1000건만 수신 |
| 초당/분당 제한 | **미관측** | 150회를 평균 0.23초 간격(약 4.3회/초)으로 연속 호출해도 제한 없음 |
| 일일 호출 한도 | **≥ 150회** (하한 실측) | 150회 연속 호출에 한도 신호 0. 절대 수치는 비공개 |

1회 행 한도를 초과하면 응답이 조용히 잘린다. `list_total_count`와 수신 행 수를 비교해
`SourceResponseTruncated`로 감지하도록 구현했다 — 감지하지 않으면 데이터가 빠진 채
커버리지만 갱신되어 영영 메워지지 않는다(헌법 원칙 V).

365일 청크는 최대 245건이라 1000건 한도에 여유가 크다.

### 일일 호출 한도 조사 결과 (T114, 2026-08-30)

**결론: 절대 수치는 확인할 수 없으나, 확인할 필요가 없음이 확인됐다.**

수치를 찾지 못한 경로 세 가지 — 셋 다 근거를 남긴다.

| 경로 | 결과 |
|------|------|
| 공식 개발명세서 `https://ecos.bok.or.kr/api/` | 클라이언트 렌더링 SPA. 서버 HTML에 제목만 있고 한도 서술 없음 |
| 응답 헤더 | `X-RateLimit-*` 류 없음. `Transfer-Encoding`·`Set-Cookie`·`Date`·`Content-Type`이 전부 |
| 웹 검색 | "개발계정 일 10,000회"라는 전언이 있으나 출처가 공공데이터포털 일반 정책이며 ECOS 공식 문서로 확인되지 않음 |

마지막 항목은 **채택하지 않는다.** R1이 처음부터 기각한 "통념상 알려진 수치"에 해당하며,
검증되지 않은 숫자를 설계 전제로 넣지 않는다는 판단은 그대로 유효하다.

대신 우리에게 실제로 필요한 명제를 직접 측정했다. 필요한 것은 "한도가 몇인가"가 아니라
"우리 백필이 하루 안에 들어가는가"(SC-005)다.

| 측정 | 값 |
|------|-----|
| 연속 호출 수 | 150회 (전체 백필 약 146회와 같은 규모) |
| 소요 시간 | 34.5초, 평균 0.230초/회 |
| 한도 신호(`INFO-300`) | **0회** |
| 정상 응답 / `INFO-200` | 120 / 30 (주말 요청이 의도대로 `INFO-200`) |

전체 백필이 약 146회이므로 실측 하한(150회) 안에 들어간다. **설정 기본값은 조정하지 않는다.**

- 청크 크기 365일 유지 — 더 잘게 쪼개면 호출 수만 늘어 한도에 불리하다(R2)
- 청크 간 대기 1000ms 유지 — 4.3회/초에서도 제한이 없었으나, 백필은 일회성이고
  146회 × 1초 ≈ 2.5분이면 끝난다. 알 수 없는 한도를 향해 속도를 올릴 이득이 없다

**남는 위험**: 하한만 알 뿐 상한을 모른다. 다른 자산군이 추가되어 같은 키로 하루 수천 회를
호출하게 되면 이 측정은 근거가 되지 못한다. 그 시점에 재측정하거나 운영계정 전환을 검토한다.
설계가 한도 수치를 전제하지 않으므로(3중 방어) 그때도 코드 변경은 필요 없다.

## R2. 청크 크기와 대기 시간 기본값

**Decision**:

| 설정 | 기본값 | 근거 |
|------|--------|------|
| 백필 청크 크기 | **365일** | USD 63회 / JPY 50회 / EUR 33회, 전체 백필 약 146회 호출 |
| 증분 청크 크기 | **365일** | 증분 공백은 통상 수일이라 1회 호출로 끝남 |
| 청크 간 최소 대기 | **1000ms** | 초당 제한 미확인 상태의 보수적 값 |
| 통화별 동시 호출 수 | **1** | FR-015a의 통화별 단일 작업과 일관 |
| 통화 간 동시 실행 | **3** (통화 수만큼) | FR-015c가 통화 간 병행을 허용 |

**Rationale**: 사용자 요구는 "전 구간을 한 번에 요청하지 않는다"이지, "잘게 쪼갠다"가 아니다.
한도가 호출 *횟수* 기준일 가능성이 높으므로 **청크를 잘게 쪼갤수록 오히려 한도를 빨리 소진한다**.
365일 청크는 전체 백필을 약 146회로 끝내면서(어떤 현실적 일일 한도에도 여유), 청크당 응답이 약 260행에
불과해 타임아웃 위험도 없고, 실패 시 재시도 단위가 1년이라 재개 손실도 작다.

**Alternatives considered**:
- 30일 청크 → 전체 약 1,780회. 재개 granularity는 좋아지지만 호출 수가 12배. 기각.
- 5년 청크 → 전체 약 30회로 가장 적지만, 실패 시 5년치를 다시 요청. 이득 대비 재개 손실이 큼. 기각.
- 행 수 기준 청킹(`startRow`/`endRow`) → 날짜 구간과 매핑이 불명확해 커버리지 기록이 어려움.
  날짜 기준 청킹을 채택. 기각.

## R3. 731Y001의 실제 최초 제공일

**Decision**: 사전 확인 없이, 런타임에 발견해 기록한다. 백필은 **통화별 탐색 시작일**
(`ECOS_PROBE_START_USD` 등 설정값, 미설정 시 전역 하한 `ECOS_PROBE_FLOOR`)부터 시작하되,
선두 청크가 `INFO-200`(데이터 없음)을 반환하면 그 구간을 "제공 없음"으로 커버리지에 기록하고
다음 청크로 진행한다. 값이 처음 나타난 날짜를 해당 통화의 실제 최초 제공일로 저장하고 UI에 노출한다.

탐색 시작일은 **실측일보다 한 청크 앞**에 둔다(예: USD 실측 1964-05-04 → `1964-01-01`).
실측일을 그대로 쓰면 "그날이 최초"라고 단정하는 셈이고 그 앞에 데이터가 있어도 보지 못한다.
한 청크 앞에서 시작하면 경계가 `INFO-200`으로 증명된다 — 통화당 1회 추가 호출이 대가다.

기존 커버리지가 탐색 시작일보다 늦게 시작하면 **역방향 백필**로 앞 구간을 먼저 채우고,
커버리지의 `covered_from`을 앞당긴다. 이미 발견해 기록한 최초 제공일보다 이른 날짜를
찾으면 그 값으로 갱신한다.

**Rationale**: 인증키 없이는 사전 확인이 불가능하다. 그런데 이 값을 미리 알아야 할 이유가 없다 —
`INFO-200`은 이미 정상 응답으로 처리하기로 되어 있고(계약 테스트 대상), 커버리지 기록 구조가
"시도했고 값이 없음"을 표현할 수 있다. 통화마다 최초 제공일이 다를 수도 있는데, 런타임 발견은
이 경우도 자동으로 처리한다.

**Alternatives considered**:
- **전 통화 공통 시작일(1995-01-01)** → 2026-08-30 실측에서 USD가 1964-05-04, JPY가
  1977-04-01부터 제공됨이 드러났다. USD 31년·JPY 18년치가 조용히 잘렸고, 잘린 구간은
  오류를 내지 않으므로 아무도 알아채지 못했다. 헌법 v4.1.0이 이 사건을 계기로 시작일
  하드코딩을 MUST NOT으로 규정했다. **기각(실제 결함으로 확인됨)**.
- 이진 탐색으로 최초 제공일 탐지 → 추가 호출을 소비하며, 순차 백필이 어차피 같은 정보를 얻음. 기각.

**남은 위험**: 커버리지를 `(covered_from, covered_through)` 한 구간으로 표현하므로 역방향
백필이 중간에 끊기면 `[1964, 1980] + [1995, 2026]`처럼 구멍이 생겨도 한 행으로는
표현할 수 없다. 현재는 역방향 백필을 앞에서부터 순차 진행해 연속성을 유지하는 것으로
대응한다. 구멍을 허용해야 할 상황이 생기면 data-model의 "왜 구간 하나인가" 결정을
다시 검토해야 한다.

## R4. 진행률 스트리밍: WebSocket vs SSE

**Decision**: **SSE (Server-Sent Events)**를 사용한다.

**Rationale**: 진행률은 서버→클라이언트 단방향이다. SSE는 브라우저에 자동 재연결이 내장되어
있어 수집이 수 분간 이어질 때 연결 끊김 복구를 직접 구현하지 않아도 된다. FastAPI에서 별도
의존성 없이 `StreamingResponse`로 제공 가능하다. 헌법 원칙 VII은 "WebSocket 또는 SSE"를 모두 허용한다.

**Alternatives considered**:
- WebSocket → 양방향이 필요 없는데 연결 수명 관리와 재연결을 직접 구현해야 한다.
  다른 자산군에서 실시간 양방향이 필요해지면 그때 도입한다(YAGNI, 원칙 IX). 기각.
- 폴링 → SC-009(갱신 공백 10초 이내)를 만족시키려면 짧은 주기 폴링이 필요해 낭비. 기각.

## R5. 차트 다운샘플링 알고리즘

**Decision**: **LTTB(Largest-Triangle-Three-Buckets)**를 서버 측에서 적용하고, 클라이언트 요청의
목표 포인트 수를 파라미터로 받는다.

**Rationale**: 이 선택은 헌법 원칙 V가 결정한다. 평균·OHLC 집계 방식은 **원본에 없던 값을 만들어낸다** —
"임의 보간 금지"에 정면으로 걸린다. LTTB는 원본 데이터 포인트 중 시각적으로 중요한 것을 *선택*할 뿐
새 값을 생성하지 않으므로 원칙 V를 위반하지 않으면서 SC-006(조작 1초 이내)을 달성한다.
결측 구간은 포인트를 만들어 채우지 않으므로 FR-032와도 일관된다.

**Alternatives considered**:
- 구간 평균 집계 → 원본에 없는 값 생성. 원칙 V 위반. 기각.
- 균등 간격 샘플링 → 값을 만들지는 않지만 극값(환율 급등락)을 놓쳐 추이를 왜곡. 기각.
- 클라이언트 측 다운샘플링 → 8,400개 전체를 전송해야 하므로 응답성 목표에 불리. 기각.

## R6. 통화별 단일 수집 작업 보장 (FR-015a)

**Decision**: 표준 SQL만 쓰는 **잠금 테이블** `fx_collection_lock`으로 강제한다.
`currency_code`를 기본 키로 두고, 작업 시작 시 INSERT를 시도해 성공하면 락을 획득한 것으로,
기본 키 충돌로 실패하면 이미 진행 중인 작업이 있는 것으로 판단한다. 작업 종료 시 DELETE로 해제한다.

프로세스가 비정상 종료해 락이 남는 경우에 대비해 `heartbeat_at`을 둔다. 수집기는 청크를 커밋할
때마다(FR-010) 이 값을 갱신하고, `heartbeat_at`이 설정된 임계값보다 오래된 락은 회수 가능한
스테일 락으로 간주한다.

**Rationale**: 헌법 v4.1.0이 "특정 DB에만 존재하는 문법(생성 컬럼, 부분 인덱스 등)에 도메인·저장
계층이 직접 의존해서는 안 된다"를 MUST로 규정한다. 기본 키 INSERT 충돌은 모든 RDBMS에서 동일하게
동작하는 유일한 이식 가능 수단이며, ORM으로도 자연스럽게 표현된다. 청크 커밋이 이미 주기적으로
일어나므로 하트비트 갱신에 추가 비용이 없다.

**Alternatives considered**:
- **MySQL 생성 컬럼 + UNIQUE 인덱스** (v2.0.0의 기존 결정) → `IF(status='running', ...)` 형태의
  생성 컬럼은 MySQL 전용이다. 헌법 v4.0.0의 DB 종속 문법 금지에 정면으로 걸린다. **기각**.
- **PostgreSQL 부분 유니크 인덱스** → 더 깔끔하지만 MySQL에 없다. 현재 기본 DB가 MySQL이므로
  채택 불가이며, 어느 쪽을 택해도 다른 DB에서 깨진다. 기각.
- **`SELECT ... FOR UPDATE` 비관적 잠금** → 표준이지만 트랜잭션을 수집 작업 전체(수 분~수 시간)
  동안 열어두어야 한다. 커넥션 풀을 고갈시키고 청크별 커밋(FR-010)과 양립하지 않는다. 기각.
- **`asyncio.Lock`** → 단일 프로세스 내에서만 유효. 재시작 시 상태가 사라진다. 기각.

## R7. 수치 정밀도와 ORM 타입 매핑 (헌법 원칙 VI)

**Decision**:

| 대상 | ORM 타입 | DB 타입 |
|------|----------|---------|
| 매매기준율 | `Numeric(18, 6, asdecimal=True)` | `DECIMAL(18,6)` |
| 스프레드 비율 | `Numeric(9, 6, asdecimal=True)` | `DECIMAL(9,6)` |
| 파생 환율 | 저장하지 않음 | — |

파생 환율 산출은 Python `Decimal`로 계산하고, 표시 직전에 `quantize(Decimal('0.01'), ROUND_HALF_UP)`
으로 소수 둘째 자리까지 반올림한다. 반올림은 **표시 단계에서 한 번만** 수행하며 중간 계산에서는
하지 않는다.

**검증됨**: `Numeric(18, 6, asdecimal=True).python_type`이 `decimal.Decimal`임을 Python 3.14.7 +
SQLAlchemy 2.0.52에서 확인했다.

**Rationale**: 헌법 원칙 VI는 코드의 `float`뿐 아니라 **ORM 모델 필드가 부동소수점으로 매핑되는
것도 금지**한다(v3.0.0에서 추가). SQLAlchemy는 `Float`와 `Numeric`을 모두 제공하므로 모델 정의에서
`Numeric` + `asdecimal=True`를 명시해야 한다. `asdecimal`은 기본값이 `True`지만, 실수로 뒤집히면
조용히 정밀도가 손실되므로 명시적으로 적는다.

**Alternatives considered**:
- `Float` 사용 → 헌법 원칙 VI 위반. 기각.
- 정수 최소단위(전) 저장 → 이식성은 좋으나 통화별 소수 자릿수가 달라 자산군 확장 시 복잡해진다. 기각.

## R8. 영업일 판정과 "직전 영업일" (FR-018a)

**Decision**: 별도의 휴장일 캘린더를 두지 않는다. 판정은 **수집 커버리지 + 값 존재 여부**로 한다.

- 고시 없는 날 = "수집이 완료된 구간에 속하는데 값이 없는 날"
- 직전 영업일 = "수집 완료 구간 안에서 값이 존재하는, 가장 가까운 이전 날짜"

**Rationale**: ECOS가 값을 주지 않은 것이 곧 "고시 없음"의 정의다. 별도 공휴일 캘린더를 두면
그 자체가 또 하나의 데이터 소스가 되어 유지보수 대상이 되고, 캘린더와 실제 고시가 어긋나면
어느 쪽이 진실인지 판단할 수 없다. 이미 있는 커버리지 정보로 충분하므로 YAGNI(원칙 IX)에 맞다.
FR-006(고시 없는 날을 미수집으로 오인하지 않기)이 요구하는 커버리지 구조가 이 판정의 기반을 겸한다.

**Alternatives considered**:
- 한국 공휴일 라이브러리 도입 → 은행 휴무일과 완전히 일치하지 않으며, 30년치 과거 공휴일 정확도가
  불확실하다. 실제 고시 데이터가 이미 정답을 담고 있으므로 불필요. 기각.

## R9. 스키마 마이그레이션 도구

**Decision**: **Alembic**을 사용한다. 마이그레이션 스크립트는 ORM 모델 메타데이터를 기준으로
생성하되, 자동 생성 결과는 반드시 사람이 검토한 뒤 커밋한다.

**Rationale**: 헌법 v4.1.0이 "스키마 변경은 **ORM 마이그레이션 도구로** 관리해야 한다"를 MUST로
규정한다. ORM이 필수가 된 이상 SQLAlchemy는 이미 의존성이므로, v2.0.0 시점에 Alembic을 기각했던
사유("SQLAlchemy 전체를 끌어와야 한다")가 소멸했다. Alembic은 SQLAlchemy 공식 도구이며 DB 방언
차이를 흡수하므로, 향후 RDBMS 교체 시 마이그레이션을 다시 쓰지 않아도 된다.

**검증됨**: Alembic 1.19.1이 Python 3.14.7에서 정상 임포트됨을 확인했다.

**주의**: Alembic의 `--autogenerate`는 인덱스·제약·타입 변경을 놓치거나 잘못 추론하는 경우가 있다.
생성된 리비전을 그대로 커밋하지 않고 검토하는 절차를 태스크에 포함한다.

**Alternatives considered**:
- **순수 SQL 파일 + 자체 러너** (v2.0.0의 기존 결정) → 헌법 v4.0.0의 "ORM 마이그레이션 도구" MUST에
  위배된다. 또한 DB 교체 시 모든 SQL을 다시 작성해야 해 교체 비용을 낮추려는 개정 취지에 어긋난다.
  **기각**.
- **마이그레이션 없이 `create_all()`** → 헌법이 수동 DDL과 동등하게 금지한다. 운영 데이터가 있는
  상태에서 스키마를 바꿀 수 없다. 기각.

## R10. 비동기 DB 드라이버 선택

**Decision**: **`aiomysql`**을 기본 드라이버로 사용하고 연결 URL을 `mysql+aiomysql://`로 구성한다.
성능이 문제가 되면 `mysql+asyncmy://`로 URL만 바꿔 교체한다.

**Rationale**: 두 드라이버 모두 Python 3.14.7에서 정상 동작함을 확인했다(R11). `aiomysql`은 순수
파이썬이라 새 Python 버전에서 휠 부재로 막힐 위험이 없고 스택 트레이스를 따라가기 쉽다. `asyncmy`는
Cython 기반이라 빠르지만, 현재 데이터 규모(약 25,000행)에서 드라이버 성능은 병목이 아니다.

드라이버는 SQLAlchemy 연결 URL 뒤에 숨으므로 애플리케이션 코드에 노출되지 않는다. 헌법 v4.1.0의
"DB 종속 요소를 격리한다"는 요구와 같은 구조다.

**필수 동반 의존성 — `cryptography`**

MySQL 8.0부터 기본 인증 플러그인이 `caching_sha2_password`다. `aiomysql`의 기반인 PyMySQL은 이
인증을 처리할 때 RSA 키 교환에 `cryptography` 패키지를 요구하며, 없으면 접속 시점에 실패한다.

```
RuntimeError: 'cryptography' package is required for
              sha256_password or caching_sha2_password auth methods
```

**실측 확인** (2026-08-30): 이 저장소의 대상 서버는 **MySQL 9.6.0 Community Server**이며,
`cryptography` 미설치 상태의 PyMySQL 2.2.8에서 위 오류가 재현됐다. 따라서 `cryptography`를
**선택이 아닌 필수 의존성**으로 선언한다(tasks T002).

`asyncmy`로 교체하더라도 동일한 인증 플러그인을 상대하므로 이 의존성은 유지된다.

**Alternatives considered**:
- `asyncmy`를 기본으로 → 지금 필요 없는 성능을 위해 빌드 의존성을 떠안는다(YAGNI, 원칙 IX). 기각.
- 동기 드라이버 + 스레드 풀 → 헌법 원칙 I(비동기 우선) 위반. 기각.
- DB 사용자를 `mysql_native_password`로 생성해 `cryptography`를 피하기 → MySQL 9.x에서 해당
  플러그인은 기본 비활성이며 보안상 후퇴다. 기각.

## R11. Python 3.14 호환성 검증

**Decision**: Python **3.14.x**를 사용한다. 헌법 v4.1.0이 지정한 버전이며, 필요한 스택 전체가
실제로 동작함을 확인했다.

**검증 결과** (Python 3.14.7, 2026-08-30 실측)

| 패키지 | 버전 | 임포트 |
|--------|------|:------:|
| SQLAlchemy | 2.0.52 | ✓ |
| Alembic | 1.19.1 | ✓ |
| aiomysql | 0.3.2 | ✓ |
| asyncmy | 0.2.14 | ✓ |
| greenlet | 3.5.5 | ✓ |

`create_async_engine`으로 `mysql+aiomysql`·`mysql+asyncmy` 두 URL 모두 커넥션 풀

**적용됨** (T003): `backend/.venv`를 Python 3.14.7로 재생성하고 위 스택 전체의 설치·임포트를
확인했다. `backend/pyproject.toml`도 `requires-python = ">=3.14"`로 갱신했다(T002).

## R12. 멱등 upsert의 이식성 (FR-003, 헌법 원칙 V)

**Decision**: upsert는 `repository` 계층의 **단일 헬퍼 함수 한 곳**에만 두고, 그 안에서 SQLAlchemy의
방언별 구문(MySQL `on_duplicate_key_update`, PostgreSQL `on_conflict_do_update`)을 분기한다.
도메인·서비스 계층은 이 헬퍼만 호출하며 방언을 알지 못한다.

**Rationale**: 헌법 v4.1.0이 "upsert 구문 같은 DB 종속 문법에 도메인·저장 계층이 직접 의존해서는
안 되며, 필요하면 ORM의 방언 추상화 뒤에 격리해야 한다"를 MUST로 규정한다. upsert는 표준 SQL에
없으므로 격리가 유일한 방법이다. 한 함수로 모으면 DB 교체 시 손댈 지점이 그 함수 하나가 된다.

**Alternatives considered**:
- `SELECT` 후 분기해 `INSERT`/`UPDATE` → 표준 SQL만 쓰지만 경쟁 조건이 생기고 왕복이 2배가 된다.
  30년치 백필에서 비용이 크다. 기각.
- ORM `session.merge()` → 이식 가능하지만 행마다 `SELECT`를 발생시켜 대량 삽입에 부적합. 기각.
- 각 리포지토리가 방언 구문을 직접 사용 → 헌법 MUST 위반. 기각.

## R13. 프론트엔드 → 백엔드 교차 출처 처리

**Decision**: Next.js **rewrite 프록시**로 동일 출처를 만든다. 백엔드에 CORS를 열지 않는다.
`next.config.ts`가 `/api/fx/:path*`를 `BACKEND_URL`(기본 `http://localhost:${BE_PORT:-8080}`)로
넘기고, 프론트엔드 코드는 절대 URL 없이 상대 경로만 쓴다.

**Rationale**: 프론트엔드(3030)와 백엔드(8080)는 포트가 달라 브라우저 기준 교차 출처다.
프록시를 두면 CORS 문제 자체가 사라진다 — 허용 출처 목록을 환경마다 관리할 필요가 없고,
프리플라이트도 없다. 특히 진행률 스트림이 `EventSource`(SSE)인데, `EventSource`는 커스텀
헤더를 붙일 수 없어 CORS 우회가 까다롭다(R4에서 SSE를 택한 대가). 동일 출처면 이 제약이
아예 성립하지 않는다.

**검증됨**(2026-08-30): 3030을 통해 `GET /api/fx/spreads`·`/api/fx/coverage`·`/api/fx/rates/*`가
정상 프록시되고, `GET /api/fx/progress`의 SSE 프레임(`event:`/`data:`)이 버퍼링 없이
그대로 통과함을 확인했다.

**Alternatives considered**:
- **백엔드 `CORSMiddleware`에 허용 출처 등록** → 출처 목록이 환경별 설정 대상으로 늘고,
  SSE와 프리플라이트를 따로 신경 써야 한다. 기각.
- **`allow_origins=["*"]`** → 설정은 가장 간단하지만 자격 증명을 붙이는 순간 못 쓰게 되고,
  운영에 그대로 나갈 위험이 크다. 기각.
- 프론트엔드가 절대 URL로 직접 호출 → 지금까지의 상태. 브라우저에서 동작하지 않는다.
  `curl` 기반 검증(quickstart)만으로는 드러나지 않았다. 기각.
