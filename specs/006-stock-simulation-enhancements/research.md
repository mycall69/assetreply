# Research: 주식 시뮬레이션 개선 — 시작일·종목 검색·환전

**Feature**: `006-stock-simulation-enhancements` | **Date**: 2026-10-02 | **Spec**: [spec.md](./spec.md)

명세가 설계로 미룬 결정과, 설계 중 확인한 사실을 정리한다. 키움증권 REST API에 대한 사실은
공식 저장소의 API 명세(`kiwoom/_data/kiwoom_api_spec.json`)와 예제, 공식 소개 페이지에서
확인했다(맨 끝 출처). **확인하지 못한 것은 확인하지 못했다고 적는다.**

---

## R6-1. 키움 어댑터의 모양

**Decision**: `backend/src/ingestion/kiwoom/`에 어댑터를 둔다(`client.py`·`parse.py`·
`errors.py`). aiohttp로 직접 호출한다. 공식 클라이언트 패키지를 들이지 않는다.

**확인한 사실 (공식 명세)**

| 항목 | 내용 |
|------|------|
| 도메인 | 실전 `https://api.kiwoom.com`, 모의 `https://mockapi.kiwoom.com` |
| 토큰 발급 | `POST /oauth2/token`, 본문 `{grant_type: "client_credentials", appkey, secretkey}` |
| 토큰 응답 | `token`, `token_type`(bearer), `expires_dt`(KST `YYYYMMDDHHMMSS`), `return_code`, `return_msg` |
| 요청 헤더 | `api-id`, `authorization: Bearer …`, `Content-Type: application/json;charset=UTF-8` |
| 연속조회 | **응답 헤더**의 `cont-yn`이 `Y`면 `next-key`를 다음 요청 헤더에 실어 보낸다 |
| 성공 판정 | 본문 `return_code`가 `0`(또는 없음)이면 성공. **HTTP 200이어도 실패일 수 있다** |
| **오류 응답의 모양 (T005 실측)** | **HTTP 200, `return_code`는 넓은 분류(인증 실패는 `3`), 세부 코드는 `return_msg`의 `[NNNN:…]`에만 있다.** 예: `{"return_code":3,"return_msg":"인증에 실패했습니다[8001:App Key와 Secret Key 검증에 실패했습니다]"}`. 그래서 **세부 코드를 메시지에서 뽑아 판정**하고, 없으면 `return_code`로 판정한다 |
| 오류 코드 | 호출 한도 `1700·1701·1702`, 인증정보 `8001·8002·8011·8012`, 토큰 `8003·8005·8006·8009·8015·8016`, 모드 불일치 `8030·8031`, 모의 미지원 `8104` |

**Rationale**

- 필요한 호출이 둘(토큰 발급, 목록 조회)뿐이다. 공식 클라이언트는 337개 API와 웹소켓·토큰
  저장소를 함께 들고 오며, 토큰을 **파일에 저장하는** 경로가 있다 — FR-061(토큰을 남기지
  않는다)과 정면으로 부딪힌다.
- ECOS 어댑터(001)·Yahoo 어댑터(005)와 같은 모양이라 계층 검사(`test_layer_boundaries`)를
  그대로 확장할 수 있다.
- **HTTP 200 + `return_code≠0`을 실패로 판정해야 한다.** ECOS가 오류를 200으로 주던 것과 같은
  함정이다(001). 상태 코드만 보면 실패 응답을 빈 목록으로 읽어 **전 종목을 "목록에서 빠짐"으로
  바꾼다** — R6-4의 축소 검사가 두 번째 방어선이다.

**토큰은 메모리에만 둔다.** 만료 10분 전에 갱신한다. DB·파일·로그·수집 기록에 쓰지 않는다
(FR-060, FR-061). 토큰 발급 응답은 원본 보관 대상이 아니다.

**실전·모의 선택은 설정이다**(`KIWOOM_MODE=real|mock`, 기본 `real`). 앱 키가 모드별로 따로
발급되므로(`8030·8031` 모드 불일치) 키와 모드가 어긋나면 인증 실패로 다룬다(R6-3).

**Alternatives considered**

- 공식 클라이언트 사용 — 토큰 파일 저장과 의존성 크기 때문에 기각.
- 비공식 `kiwoom-rest-api` 패키지(헌법 스택 표에 이름이 있다) — 목록 조회 둘만 쓰는데 의존성을
  더할 이유가 없다. 헌법 표는 "쓸 수 있다"이지 "써야 한다"가 아니다.

## R6-2. 무엇을 어떤 단위로 받는가

**Decision**: 목록을 **5개 단위**로 받는다. 단위가 곧 교체·기준 시각·재시도의 단위다(FR-015).
**ETF·리츠는 따로 받지 않고 KOSPI 목록 안에서 `marketName`으로 가른다**(T005 실측, 2026-10-02).

| 단위 | 출처 요청 | 실측 건수 (2026-10-02) | 남기는 것 |
|------|-----------|------------------------|-----------|
| `KOSPI` | 국내 목록 `mrkt_tp=0` | 2,480 | `marketName`이 `거래소`(주식 916)·`ETF`(1,171)·`리츠`(23) |
| `KOSDAQ` | 국내 목록 `mrkt_tp=10` | 1,825 | 전부(`코스닥`) |
| `NYSE` | 미국 목록 `stex_tp=NY` | 5,581 | 전부 |
| `NASDAQ` | 미국 목록 `stex_tp=ND` | 5,211 | 전부 |
| `AMEX` | 미국 목록 `stex_tp=NA` | 1,953 | 전부 |

남기는 종목은 국내 3,935건, 미국 12,745건이다.

**확인한 사실 (T005, 실제 응답)**

- **단위마다 한 쪽에 전부 온다.** 응답 헤더 `cont-yn`이 `Y`가 아니다. 미국 목록의 분당 5회 제한은
  단위마다 한 번만 부르므로 걸리지 않는다. 쪽 사이 간격 설정(`KIWOOM_US_PAGE_DELAY_SECONDS`)은 쪽이
  나뉘어 오게 될 때를 위해 남긴다.
- **KOSPI 목록(`mrkt_tp=0`)에 ETF·리츠·ETN이 이미 들어 있다.** `marketName` 분포는 거래소 916, ETF
  1,171, 리츠 23, ETN 358, ETN(변동성) 8, ETN(손실제한) 1, 인프라투자금융 2, 뮤추얼펀드 1이다.
  `mrkt_tp=8`(ETF)·`mrkt_tp=6`(리츠)의 응답은 이 KOSPI 목록의 **부분집합**이다(코드가 전부 겹친다).
  처음 설계처럼 ETF·리츠를 별도 단위로 받으면 같은 종목이 두 단위에 속해, 어느 단위가 먼저 갱신되느냐에
  따라 종목의 단위가 뒤바뀐다.
- **남기지 않는 것**: ETN 세 종류(Clarifications Q1), 인프라투자금융·뮤추얼펀드(명세 범위 밖).
  **처음 보는 `marketName`이 나오면 그 단위의 갱신을 `invalid`로 실패시킨다** — 조용히 빼면 출처가
  이름을 바꿨을 때(예: `거래소` → `유가증권`) 주식 916건이 오류 없이 "목록에서 빠짐"이 된다. 그 감소는
  2,112 → 1,196(57%)이라 축소 검사(FR-018a, 50%)로도 잡히지 않는다.
- 국내 응답 `list[]`의 필드: `code`, `name`, `kind`, `listCount`, `regDay`(상장일 `YYYYMMDD`),
  `lastPrice`, `state`, `marketCode`, `marketName`, `upName`, `upSizeName`, `companyClassName`,
  `orderWarning`, `auditInfo`, `nxtEnable`. 숫자는 0으로 앞을 채운 문자열이다.
- **국내 종목코드는 6자리지만 숫자만은 아니다**(`0030R0` 대신밸류리츠, `0000D0` 등). 검증은 "6자리"로
  하고 "숫자 6자리"로 하지 않는다.
- 미국 응답 `list[]`의 필드: `stex_tp`, `stk_cd`, `stk_nm`, `stk_enm`, `mkgb`, `upgb`, `isEtf`.
  **12,745건 모두 한글 종목명(`stk_nm`)이 있다**(`AAPL` → 애플, `TSLA` → 테슬라). 일부 ETF는 한글명이
  영문 표기다(`SPY` → "S&P 500 SPDR ETF").
- `isEtf`는 `Y` 5,729 / `N` 7,004 / 빈 값 12건이다. 빈 값은 `stock`으로 둔다.
- 미국 티커 표기는 다섯 갈래다 — R6-6의 표.

**Rationale**: 미국을 `stex_tp=%`(전체)로 한 번에 받으면 한 거래소의 실패가 셋을 함께 잃게 한다.
단위를 나누면 실패가 그 단위에 갇힌다(FR-015, FR-018).

**남은 확인 사항**: 없음. 처음의 "확인하지 못한 것" 셋(쪽당 건수, 응답 예시의 실제성, 미국 ETF 포함 여부)은
T005로 모두 확인했다. 공식 응답 예시가 자리 표시용이라는 점은 그대로이며, **계약 테스트 픽스처는 실제
응답이다**(헌법 원칙 III).

## R6-3. 갱신을 언제, 누가 하는가

**Decision**: 검색 요청은 **갱신을 요청만 하고 기다리지 않는다.** 실제 갱신은 앱 수명과 함께 사는
**목록 갱신 워커**(`worker/listing_worker.py`)가 한다. 005의 주식 수집 워커와 같은 모양이다.

검색이 들어오면 단위마다 다음을 본다.

1. 오늘(KST) 이미 온전히 받았다 → 아무것도 하지 않는다(FR-013)
2. 받는 중이다 → 아무것도 하지 않는다(FR-014)
3. **인증 실패로 막혀 있다** → 아무것도 하지 않는다(FR-013b)
4. 마지막 실패 후 간격(기본 30분)이 지나지 않았거나 오늘 시도가 상한(기본 5회)에 닿았다 →
   아무것도 하지 않는다(FR-013a)
5. 그 밖 → 갱신을 큐에 넣는다

**중복 차단은 DB 점유로 한다**(FR-014). 단위별 점유 행을 기본 키 INSERT로 잡는다 — 005의
`stock_collection_lock`과 같은 방식이며, 기본 키 충돌이 "이미 진행 중"이라는 신호다(헌법 DB
운영 규약). 큐의 중복 거르기는 비용 절약일 뿐 정합성의 근거가 아니다.

**인증 실패 막힘은 프로세스 메모리에 둔다.** 인증 정보는 `.env`에서 기동 시 읽으므로, 사용자가
고치면 백엔드를 다시 띄우게 되고 그때 막힘이 풀린다(FR-013b "고친 뒤에는 같은 날이라도").
DB에 두면 인증 정보를 고친 뒤에도 그날 내내 막혀, 고친 것이 효과가 없다고 읽힌다.
DB의 갱신 기록에는 **실패 종류와 사유**만 남긴다(키·토큰 없이).

**실패 종류를 넷으로 나눈다** — 재시도 여부가 다르기 때문이다.

| 종류 | 판정 | 재시도 |
|------|------|--------|
| `auth` | 인증정보·토큰·모드 불일치 코드, HTTP 401 | 그날 하지 않는다(프로세스 재시작 전까지) |
| `rate_limit` | `1700·1701·1702` | 간격 뒤 |
| `network` | 연결 실패·시간 초과·5xx | 간격 뒤 |
| `invalid` | 형식 오류, R6-4의 축소 검사 | 간격 뒤 |

**Rationale**: 검색이 다운로드를 기다리면 그날 첫 검색이 수 분 걸린다(FR-017). 미국 목록은
분당 제한 때문에 특히 길다.

**Alternatives considered**: 매일 정해진 시각에 받는 스케줄러 — 사용자가 "그날 처음 시도할 때"를
요청했고, 쓰지 않는 날에도 출처를 부르게 되어 기각.

## R6-4. 교체를 어떻게 원자적으로 하는가

**Decision**: 한 단위의 **모든 쪽을 메모리에 받은 뒤** 검사를 통과하면 한 트랜잭션에서 교체한다.

1. 모든 쪽을 받는다. 중간에 하나라도 실패하면 **아무것도 바꾸지 않는다**(FR-018)
2. 검사한다 — 비어 있지 않은가, 필수 필드가 있는가, **이전 목록보다 설정한 비율(기본 50%) 이상
   줄지 않았는가**(FR-018a)
3. 한 트랜잭션에서: 받은 종목을 upsert하고(`last_seen_at` 갱신), **그 단위에 속했는데 이번에 없는
   종목을 "목록에서 빠짐"으로 표시**하고(지우지 않는다, FR-019), 갱신 기록의 기준 시각을 바꾼다

**축소 검사가 필요한 이유**: 출처가 오류 없이 일부만 주면(쪽이 끊겼는데 `cont-yn=N`, 또는
`return_code=0`인 빈 목록) R6-1·R6-3의 실패 판정을 통과한다. 그대로 바꾸면 빠진 종목이 모두
"목록에서 빠짐"이 되어 상장폐지된 것처럼 보인다. 실제 상장폐지는 하루에 몇 건이라 50%는
충분히 넉넉하다. 비율은 설정이다.

**단위를 옮긴 종목**(코스닥 → 코스피 이전상장): 종목은 국내 코드로 식별하므로 행은 하나다
(R6-6). 새 단위의 갱신이 그 행의 단위를 바꾸고, 옛 단위의 갱신은 **지금 그 단위에 속한 행만**
"빠짐"으로 표시한다. 어느 쪽이 먼저 돌든 결과가 같다.

## R6-5. 검색을 어디서 어떻게 하는가

**Decision**: 검색은 **프로세스 메모리의 색인**에서 한다. DB가 원본이고 색인은 그 사본이다.
일치 판정은 **순수 함수 모듈** `backend/src/search/`에 둔다.

**왜 SQL `LIKE`가 아닌가**: "삼성ㅈ"은 글자마다 판정 방식이 다르다 — "삼"·"성"은 그 음절이어야
하고 "ㅈ"은 초성이 ㅈ인 아무 음절이면 된다. 한 컬럼에 대한 `LIKE` 하나로 표현할 수 없고,
DB마다 다른 문법(정규식·콜레이션)에 기대면 헌법 DB 운영 규약을 어긴다.

**색인**: 종목마다 일치용 문자열을 미리 만든다.

- 이름: NFC 정규화, 공백 제거, 라틴 문자 소문자화(`casefold`)
- 초성 열: 한글 음절은 초성 자모로, 그 밖의 글자는 그대로
- 국내는 한글 종목명·종목코드, 미국은 한글 종목명·영문 종목명·티커

**일치 규칙** (FR-020~022) — 검색어도 같은 정규화를 거친 뒤, 이름의 어느 위치에서 시작해
검색어의 글자마다 다음을 만족하면 맞는다.

| 검색어 글자 | 맞는 조건 |
|-------------|-----------|
| 초성 자모(ㄱ~ㅎ, 쌍자음 포함) | 그 위치 음절의 초성이 같다. **ㅆ과 ㅅ은 다르다** |
| 완성 음절, 마지막 글자가 아님 | 음절이 같다 |
| 완성 음절, **마지막 글자이고 받침이 없음** | 초성·중성이 같다("서"는 "성"과 맞는다 — 받침 입력 대기) |
| 완성 음절, 마지막 글자이고 받침이 있음 | 음절이 같다 |
| 그 밖(라틴·숫자·기호) | 같은 글자(라틴은 소문자화 후) |

마지막 줄 전의 규칙이 없으면 "삼성"을 치는 도중의 "삼서"에서 결과가 사라졌다가 "삼성"에서 다시
나타난다(FR-022의 실패 양상). 이 규칙을 spec FR-022에 더했다.

**순위**(FR-023, Clarifications Q4): 정확 일치 → 앞부분 일치 → 포함. 같은 순위 안에서는
일치한 이름의 길이가 짧은 순 → 정규화한 이름의 코드 포인트 순(가나다·알파벳) → 시장 → 코드.
코드·티커가 검색어와 정확히 같으면 정확 일치다.

**성능**(SC-001): 색인 크기는 국내 3,935건(주식·ETF·리츠), 미국 12,745건이다(T005 실측).
미리 만든 문자열을 선형으로 훑어도 한 번에 수십 ms 안쪽이다. **SC-001의 0.5초에는 화면의 입력
대기 시간이 포함된다.** 005의 검색 대기는 300ms라 예산의 60%를 쓴다. 로컬 검색은 대기를
150ms로 줄이고, 일본 외부 검색만 300ms를 유지한다.

**색인 갱신**: 검색마다 단위별 기준 시각을 한 번 읽어(작은 질의 하나) 바뀌었으면 다시 만든다.
프로세스가 하나라는 전제(CLAUDE.md "단일 워커")에 기대지 않는다 — 여럿이어도 각자 DB 버전을 보고
따라온다.

**버전은 단위별 기준 시각의 묶음이다**(구현 단계 정정, T037). 처음에는 "기준 시각의 최댓값"이었다.
저장 시각은 초 단위라 두 단위가 같은 초에 교체되면 최댓값이 같고, 그 사이에 만든 색인이 뒤 단위를
빠뜨린 채 남는다 — 오류 없이 그 단위의 종목이 다음 날까지 검색되지 않는다. 단위마다의 기준 시각을
모두 보면 어느 단위가 바뀌어도 버전이 바뀐다.

**Alternatives considered**: 전문 검색 엔진 — 1만 건에 과하다. DB 함수 색인 — 이식성 위반.

## R6-6. 목록의 종목을 005의 시세 식별자로 옮기기

**Decision**: 옮기는 규칙을 **순수 함수 하나**(`search/price_symbol.py`)에 둔다. 005가 저장한
종목과 같은 식별자가 나와야 한다(FR-030).

| 단위 | 005 시장 | 005 심볼 | 통화 |
|------|----------|----------|------|
| `KOSPI`(주식·ETF·리츠) | `KRX` | `{code}.KS` | KRW |
| `KOSDAQ` | `KRX` | `{code}.KQ` | KRW |
| `NYSE`·`NASDAQ`·`AMEX` | 그 거래소 | 티커(시세 출처 표기) | USD |

- **ETF·리츠는 목록에서 별개 구분이지만 유가증권시장에서 거래된다**(FR-010a). 그래서 `.KS`다.
  **실제 종목 몇 개로 시세 출처에서 확인한다**(quickstart 시나리오) — 추정이 틀리면 ETF 전부가
  "시세 없음"이 된다.
- **미국은 거래소가 달라도 같은 티커면 같은 종목**이다(FR-030a). 005는 시세 출처의 거래소 코드로
  시장을 정했다(`PCX`→`AMEX` 등). 목록 출처가 같은 ETF를 `NYSE`로 분류하면, `(시장, 심볼)`로
  찾을 때 같은 종목이 둘이 된다. 그래서 미국 종목은 **기존 종목을 티커로 먼저 찾고**, 없을 때만
  목록의 거래소로 새로 만든다. 시세 출처는 미국 종목을 티커만으로 조회하므로 거래소가 달라도
  시세는 같다.
- **티커 표기 차이**(T005 실측 + 시세 출처 확인, 2026-10-02): 목록 출처는 같은 뜻을 다섯 갈래로 적는다.
  시세 출처의 표기는 실제 조회로 확인했다(모두 응답이 왔다).

  | 목록 출처 | 예 | 시세 출처 | 종류 | 건수 |
  |-----------|----|-----------|------|------|
  | 기호 없음 | `AAPL` | `AAPL` | 보통주 | 대부분 |
  | `BASE.SUF` | `BH.A`, `AAC.UN` | `BH-A`, `AAC-UN` | 클래스·유닛 | 53 |
  | `BASE` + 소문자 | `BRKb`, `BFa` | `BRK-B`, `BF-A` | 클래스 | 22 |
  | `BASE-SER` | `ABR-D`, `PHXE-` | `ABR-PD`, `PHXE-P` | 우선주(시리즈) | 318 |
  | `BASE_p` + 소문자 | `BAC_pe`, `AHT_pd` | `BAC-PE`, `AHT-PD` | 우선주(시리즈) | 61 |

  정방향은 위 표를 그대로 옮긴다. 미국 종목 12,745건 전부에서 **정방향 결과가 서로 겹치지 않고**,
  아래 역변환으로 **원래 기호가 돌아온다**(왕복 검사 실패 0건). 이 표를 계약 테스트에 고정한다(FR-031,
  SC-008). 표에 없는 기호가 새로 나타나면 그대로 보내되, 시세 출처가 모르면 "시세 출처에서 찾지 못함"으로
  알린다(FR-032).

**FR-032의 구별**: 005는 시세 출처가 종목을 모를 때(`StockSymbolNotFound`)와 받았지만 값이
없을 때(`NoPriceData`)를 이미 다른 예외로 낸다. 화면이 두 사유를 **다른 말로** 보이게 한다.

**그 예외는 수집 워커 안에서 난다**(구현 단계 확인, T025·T040). 시뮬레이션 요청은 수집을 큐에 넣고
202를 돌려줄 뿐이라, 005에서는 워커가 작업을 실패로 끝내도 다음 요청이 **같은 수집을 다시 시작했다**
— 화면은 "받고 있습니다"와 실패를 되풀이하고, 그 사유가 `price_symbol_unknown`으로 드러날 길이 없었다.
그래서 워커가 작업의 `last_error` 앞에 표지(`price_symbol_unknown: `)를 붙이고, 수집 판정
(`plan_collection`)은 **그 종목의 마지막 작업이 이 표지로 끝났으면** 수집하지 않고
`404 price_symbol_unknown`을 낸다. 진행 스트림의 `failed` 사건에는 `status: price_symbol_unknown`을
싣고 표지는 사유에서 뗀다. 005의 테이블 구조는 바꾸지 않는다(data-model).

**알려진 한계**: 이전상장(코스닥→코스피)은 시세 출처의 심볼이 `.KQ`→`.KS`로 바뀐다. 005에는
옛 심볼로 저장된 종목이 남는다. 둘을 합치지 않는다(범위 밖) — 새 심볼로 새로 받는다.

### 역변환 — 시세 식별자에서 검색용 종목 찾기 (analyze R1)

이력(브라우저, 005 형식)은 시세 식별자(시장·심볼)만 들고 있다. 이력에서 다시 실행할 때 종목이 아직
등록되지 않았으면, **시세 식별자에서 검색용 종목을 거꾸로 찾아야** 등록할 수 있다(FR-030b, R6-17).
같은 순수 함수 모듈(`search/price_symbol.py`)에 역방향을 둔다.

| 순서 | 시장 | 규칙 |
|------|------|------|
| 1 | `KRX` | 심볼에서 `.KS`·`.KQ`를 떼어 국내 종목코드로 찾는다(`country = KR`) |
| 2 | 미국 | 정방향 표의 **역으로 후보를 만든다**: `BASE-P…`는 `BASE-…`·`BASE_p…`(소문자), 그 밖의 `BASE-SUF`는 `BASE.SUF`·`BASE`+소문자. 후보 중 **목록에 있는 첫 것**을 쓴다(`country = US`). 거래소는 보지 않는다(FR-030a) |
| 3 | 미국 | 2에서 못 찾으면 심볼을 **그대로** 티커로 보고 한 번 더 찾는다 — 기호가 없는 대부분의 티커가 여기서 맞는다 |
| 4 | 모두 | 그래도 없으면 등록하지 않고 "검색에서 다시 고르세요"(`action: reselect`)로 답한다 — 일본과 같다 |

**정방향과 역방향은 왕복해야 한다.** 목록 → 시세 식별자 → 목록이 같은 종목이 아니면, 검색에서 고른
종목은 시뮬레이션되는데 같은 종목의 이력 재실행만 "알 수 없는 종목"이 된다(SC-007a). 둘 다 같은 표로
검증한다(tasks T016·T066).

- 기본값 2020-01-01은 스토어의 초기값이다(FR-001). 종목을 바꾸는 동작은 시작일을 건드리지 않는다

## R6-8. 시작 가능 날짜 (FR-005, FR-005a)

**Decision**: 판정을 **두 단계**로 한다.

1. **수집 전** — 목록의 상장일이 있으면 하한으로 쓴다. 시작일 < 상장일이면 시세를 받지 않고 막는다.
   화면은 검색 결과에 실린 상장일로 **실행 전에** 알린다(FR-005).
2. **수집 후** — 수집 범위가 시작일을 덮는데 **시작 월에 일봉이 하나도 없으면** 막고, 시세가 실제로
   시작하는 날을 알린다(FR-005a).

**005의 판정에 있던 구멍**: 005의 `run_simulation`은 `listed_on`(시세 출처의 메타데이터
`firstTradeDate`)을 받은 시세보다 **먼저** 믿는다. 메타데이터가 실제 일봉보다 이르면, 그 사이의
시작일을 받아들이고 첫 매수가 일봉이 시작하는 달로 **몰래 밀린다**(SC-013a). 수집 후에는 실제
일봉을 근거로 삼도록 바꾼다.

**"시작 월에 일봉이 없으면"인 이유**: 005의 첫 매수는 시작일 이후 첫 거래일이다. 시작일이 휴일이면
첫 거래일은 며칠 뒤가 정상이다(2020-01-01 → 01-02). 그래서 "첫 일봉 > 시작일"로 판정하면 정상적인
시작을 거절한다 — 005가 실제로 겪은 결함이다(2021-08-01 일요일 거절). 한 달 안에 일봉이 하나도 없는
경우는 휴장으로 설명되지 않는다.

**목록의 상장일을 005 종목의 `first_available_date`에 복사하지 않는다.** 그 필드는 "시세 출처가 값을
주기 시작한 날"이다. 상장일을 넣으면 위의 구멍이 그대로 열린다.

**알려진 한계**: 시작 월 안의 짧은 공백(시세 출처의 결측이 며칠)은 휴장과 구별할 수 없다.

## R6-9. 엔화 고시 단위 (FR-042)

**Decision**: 환율을 읽는 곳(`api/services/stock_fx.py`의 `load_rates`)에서 **행의 `quote_unit`으로
나눠 1단위당 값**을 만든다. 나눗셈은 `simulation/fx_convert.py`의 순수 함수(`per_unit`)가 한다.

**확인한 사실**: 001은 행마다 `quote_unit`을 저장한다(엔화 100). 005의 `load_rates`는
`{날짜: base_rate}`만 만들고 단위를 버린다. 재현(직접 계산): 원금 1,000,000원, 100엔당 900원 →
005는 1,109엔, 기대 약 110,900엔.

**Rationale**: 단위가 행에 있으므로 행 단위로 나눈다. 통화별 상수로 두면 출처가 단위를 바꿀 때
과거 행이 틀린다 — 001이 단위를 행에 복제한 이유가 그것이다.

나눗셈은 `Decimal`이고 100은 10의 거듭제곱이라 정확하다. 환율 자릿수(소수 6자리)는 유지한다.

## R6-10. 환율이 없을 때 (FR-043~047)

**Decision**: 시뮬레이션의 수집 판정(`api/services/stock_collect.py`)에 **환율 판정**을 더한다.
주식 시세 판정과 같은 202 응답에 환율 상태를 함께 싣는다(FR-045).

**필요한 구간**: 시작일부터 계산 끝(어제)까지(FR-044). 첫 매수일은 시세를 받기 전에는 모르므로
시작일로 넉넉하게 잡는다. 평가에 "가장 가까운 이전 고시일"(005 FR-041c)을 쓰므로 001의 커버리지가
그 구간을 덮는지만 보면 된다.

**수집 요청은 고쳐진 `ensure_background_job`을 거친다.** 그 함수가 003의 시작 큐(`StartQueue.request`)로
넘기고 수집 표를 돌려준다(아래 "발견한 결함"). 006의 판정이 큐를 직접 부르면 수집 표 판정이 두 곳에 생겨,
외환 화면과 시뮬레이션이 같은 상황을 다르게 말할 수 있다(analyze A1).

**한 번에 한 통화**(003 FR-004): 큐가 다른 통화를 처리 중이면 거절한다. 그 거절을 삼키지 않고
202 응답에 `waiting`과 진행 중인 통화를 싣는다(FR-046). 화면은 003의 수집 스트림을 구독하다가
끝나면 시뮬레이션을 다시 요청한다. **다시 요청하는 쪽이 화면이다** — 서버에 대기열을 따로 두면
화면을 떠난 뒤에도 수집이 시작되는데, 사용자는 그것을 요청한 적이 없다.

**수집으로 채울 수 없는 구간**(FR-043a): 001의 외환 수집은 **탐색 시작일**(`settings.probe_start(통화)`,
`ECOS_PROBE_START_*` 또는 `ECOS_PROBE_FLOOR`)부터 앞으로만 받는다. 실제 최초 고시일은 수집 중 발견해
`currency.first_available_date`에 기록한다(001 FR-002a). 그래서 판정은 둘이다.

| 순서 | 경우 | 조건 | 말 | 수집 |
|------|------|------|----|------|
| 1 | ② 수집 범위 설정 밖 | 필요한 날 < 탐색 시작일 | "환율 수집 범위가 {탐색 시작일}부터로 설정되어 있다" | 하지 않는다 |
| 2 | ① 출처에 없음 | 탐색 시작일 ≤ 필요한 날 < `first_available_date` | "그 날짜 이전의 환율은 출처에 없다" | 하지 않는다 |
| 3 | 수집 가능 | 위에 해당하지 않고 커버리지 밖 | 수집 중 | 한다 |

**②를 먼저 판정한다**(analyze N2). `first_available_date`는 출처의 진짜 최초 고시일이 아니라 **수집한 범위
안의 첫 날**이다. 탐색 시작일이 출처의 실제 시작보다 늦으면(예: 탐색 시작일 2000-01-01, 기록된 최초일
2000-01-04) 그보다 앞의 값은 출처에 있을 수 있다. 이때 ①을 먼저 보면 필요한 날 1980년을 "출처에 없음"으로
말한다 — 설정으로 풀리는 제약을 영영 불가능한 것으로 말하게 된다.

두 규칙이 없으면 수집이 끝나도 여전히 비어 다시 수집을 시작하고, 시뮬레이션은 영원히 "수집 중"에
머문다. **①과 ②를 섞어 말하지 않는다** — ②는 설정을 바꾸면 풀리는데 ①로 말하면 사용자는 영영 불가능한
것으로 읽는다. 이 규칙을 spec FR-043a로 더했다(analyze H1).

**값을 메우지 않는다**(FR-047, 헌법 원칙 V). 수집이 실패하면 사유를 알리고 끝낸다.

### 발견한 결함 — 001의 `ensure_background_job`은 작업을 실행시키지 않는다

`api/services/collection_gate.py`의 `ensure_background_job`은 작업 행을 만들고 **점유를 잡은 뒤
반환한다. 워커의 큐에 넣지 않는다.** 003의 워커는 큐에서 꺼낸 통화로 `run_once`를 돌고, `run_once`는
점유를 새로 잡으려다 이미 잡혀 있으면 `None`을 돌려주고 끝난다. 그래서 이 경로로 시작된 작업은
**아무도 실행하지 않는 채 점유만 쥐고**, 003의 정리 루프(`reconcile_loop`)가 정체로 판정할 때까지
그 통화의 수집을 막는다.

이 함수는 외환 화면의 자동 수집 경로(`routes/series.py`·`daily.py`·`rates.py`·`latest.py`)가 쓴다.

**006도 영향을 받는다.** 006은 이 함수를 직접 쓰지 않지만, 외환 화면이 먼저 이 함수로 JPY의 점유를 남겨
두었다면 006이 시작 큐로 요청해도 워커의 `run_once`가 점유를 잡지 못하고 조용히 끝난다. 시뮬레이션은
정리 루프가 회수할 때까지 "수집 중"에 머문다 — FR-046이 막으려는 "늦게 일어남"이다(analyze H2).

**Decision: 006에서 고친다.** `ensure_background_job`은 **작업도 점유도 만들지 않고** 003의 `StartQueue`로
요청만 넘긴다. 작업과 점유는 워커의 `run_once`만 만든다. 외환 화면의 자동 수집도 이때부터 실제로 돈다
(spec FR-046a). 코드 경로로 확인했고 실행으로 재현하지는 않았다 — 고치기 전에 테스트로 재현한다(tasks T091).

**작업 번호가 없을 수 있다**(analyze N1). 작업 행은 `run_once`가 만들므로(`worker/runner.py`) 큐에 넣는
시점에는 번호가 없다. 그래서 함수는 작업 번호 대신 **수집 표**를 돌려준다.

| 상황 | `state` | `jobId` | `progressUrl` |
|------|---------|---------|---------------|
| 그 통화의 점유가 있다(실행 중) | `collecting` | 점유의 작업 번호 | `/api/fx/progress?jobId={번호}` |
| 큐가 받아들였다 / 그 통화가 이미 큐에 있다 | `queued` | `null` | `/api/fx/collection/stream?currency={통화}` |
| 다른 통화가 처리 중이라 큐가 거절했다 | `waiting` (+ `busyWith`) | `null` | `/api/fx/collection/stream?currency={통화}` |

- **큐가 거절하면 아무것도 남기지 않는다.** 미리 작업을 만들면 실행되지 않는 작업이 다시 생긴다.
- 외환 화면의 202 응답(`series`·`daily`·`rates`·`latest`)은 이 표를 그대로 싣는다 — `jobId`가 `null`일 수
  있고 `state`·`busyWith`가 더해진다. **외환 화면의 프론트엔드는 `progressUrl`·`jobId`를 읽지 않는다**
  (`frontend/src/lib/types.ts`의 `SeriesCollecting`에 두 필드가 없음을 확인했다). 바뀌는 것은 백엔드 계약과
  그것을 단정하는 테스트뿐이다.
- 006의 시뮬레이션 202의 `fx`도 같은 표에서 `state`·`busyWith`를 가져온다(contracts/rest-api 5절).

**실행으로 확인한 사실 (T091, 2026-10-02)**: 고치기 전 외환 차트의 202 뒤 점유 1건이 남고, 워커가 출처를
한 번도 부르지 않았다. 위의 코드 경로 분석이 실행으로 재현됐다.

**함께 고친 것 — 스트림의 `busyWith`**(구현 단계 발견, T054·T091). 003의 통화별 스트림은 `busyWith`를
**연결할 때 한 번만** 읽어 끝까지 같은 값을 보냈다(`routes/collection.py`). 그러면 `waiting`인 화면은
다른 통화의 수집이 끝나도 그 사실을 알 길이 없어, 다시 요청할 시점을 잡지 못한다. 스트림이 프레임마다
큐의 상태를 다시 읽게 했다. 외환 화면의 표시도 그만큼 정확해진다.

**화면이 다시 요청하는 시점**(T054): `waiting`이면 `idle`의 `busyWith`가 비었을 때, `queued`·`collecting`이면
진행(`snapshot`)을 본 뒤의 `idle`, 또는 진행을 한 번도 못 보고 `idle`이 두 번 왔을 때(구독이 붙기 전에
끝난 짧은 수집). 한 번의 `idle`로 다시 요청하지 않는 이유는 워커가 큐에서 꺼내기 직전일 수 있어서다.

## R6-11. 원금 통화 제한 (FR-050~052)

**Decision**

- 서버: `check_principal_currency(principal_currency, stock_currency)`가 `{KRW, 종목 통화}` 밖이면
  `400 currency_pair_not_allowed`를 낸다. 표·차트·이력 재실행이 모두 이 함수를 지난다(FR-050a).

- 화면: 종목을 고르면 고를 수 있는 원금 통화가 정해진다. 종목을 바꿔 지금의 통화가 허용되지 않게
  되면 **값을 바꾸지 않고** "다시 고르세요" 상태로 둔다. 실행 버튼은 그동안 막힌다(FR-050b).
- 이력: 005 시절의 막힌 조합 항목은 그대로 둔다. 다시 실행하거나 비교에 고르면 거절 사유와 함께
  표시한다(FR-050c). 비교는 005의 "일부를 불러오지 못함" 경로를 그대로 쓴다.

**Rationale**: 화면만 막으면 이력의 재실행과 직접 요청이 지금처럼 조용히 계산된다. 서버의 한 함수가
판정하면 경로가 몇 개든 같은 답이 나온다.

## R6-12. 일본 종목 검색 (FR-026, FR-027)

**Decision**: 검색을 **두 엔드포인트로 나눈다.**

- `GET /api/stocks/search` — 로컬 목록(국내·미국). 외부를 부르지 않는다.
- `GET /api/stocks/search/external` — 005의 외부 출처 검색. 결과에서 **TSE만 남긴다**.

화면은 둘을 **따로** 부르고, 로컬 결과를 먼저 그린다. 외부 검색의 실패는 그 영역에만 표시한다.

**Rationale**: 한 응답으로 합치면 서버가 외부 응답을 기다려야 하고, 외부가 막히면 로컬 결과까지
늦는다(FR-027). 나누면 서로를 기다릴 방법 자체가 없다.

**늦게 온 결과**(FR-029a): 005의 검색 칸은 입력 대기 타이머만 있고 **응답 순서를 확인하지 않는다**
— 늦게 온 이전 검색의 응답이 최신 결과를 덮을 수 있다. 요청마다 번호를 붙이고, 응답의 번호가 최신이
아니면 버린다. 두 엔드포인트가 각자 번호를 가진다.

## R6-13. 원본 보관 (FR-061, 헌법 원칙 V)

**Decision**: 목록 응답의 원본을 **지우지 않는다.** 같은 본문은 한 번만 저장한다 — 본문을 SHA-256
해시를 키로 `stock_listing_raw_body`에 두고, 쪽 기록(`stock_listing_raw`)은 해시만 가리킨다. 토큰 발급
응답과 헤더는 보관하지 않는다.

**Rationale**

- 헌법 원칙 V는 "원본(raw) 응답을 보존하고 … 분리 저장해야 한다(MUST)"이며 보존 기간을 두지 않는다.
  처음 설계의 "최근 7회만 남기고 지운다"는 이 MUST를 어겼다(analyze C1). 003이 줄인 것은 **수집 사건
  기록**이지 원본 응답이 아니었다 — 같은 판단으로 볼 수 없었다.
- 용량: 중복 제거 전 추정은 하루 약 3MB(국내 약 1MB + 미국 약 2MB), 1년에 1GB 남짓이다. 목록은 날마다
  조금만 바뀌므로 같은 본문이 많다. 다만 앞쪽에 종목 하나가 들어오면 뒤쪽의 쪽 경계가 모두 밀려 그
  쪽들은 본문이 달라진다 — 중복 제거가 얼마나 듣는지는 운영하며 본다. 부족하면 압축을 더하되 **지우는
  쪽으로 가지 않는다.**

**Alternatives considered**: 압축만 하고 지우지 않기 — 본문을 DB에서 바로 읽을 수 없어 되짚기가
번거롭다. 보존 기간을 두는 헌법 개정 — 001·005의 원본까지 걸리는 별도 절차라 기각.

행으로 줄인다.

## R6-17. 고른 종목의 등록 (FR-030b) — 005에서 발견한 결함

### 발견한 결함 — 005는 고른 종목을 저장하지 않는다

`repository/stock.py`의 `ensure_stock`을 **호출하는 곳이 없다**(코드 전체를 검색해 확인했다).
시뮬레이션은 `require_stock`으로 `stock` 테이블에서 종목을 찾고, 없으면 `404 unknown_stock`을
낸다. 검색(005)은 시세 출처에 묻기만 하고 결과를 저장하지 않는다. 그래서 **실제 사용에서는 검색으로
고른 어떤 종목도 시뮬레이션되지 않는다.** 통합 테스트는 픽스처가 `stock` 행을 직접 넣으므로 통과한다
— 005의 수동 검증(T109)이 남아 있어 드러나지 않았다.

같은 이유로 **`first_available_date`도 채워지지 않는다.** 시세 출처 응답의 `firstTradeDate`를
읽기만 하고(`parse.py`) 저장하지 않는다. 그러면 005의 상장 이전 판정은 늘 "받아 둔 첫 시세"로
떨어지고, **시작일이 휴일인 정상적인 시작을 거절한다** — 005가 테스트로 잡고 `listed_on`으로 고쳤던
결함이 실제 경로에서는 그대로 살아 있다. 006의 기본 시작일 2020-01-01은 휴일이라 **기본값 그대로
실행하면 매번 거절된다**(SC-013 위반). R6-8의 "수집 후 시작 월 일봉 검사"가 이 판정을 대신하므로
`first_available_date`에 기대지 않게 된다.

### Decision

**종목을 고르는 순간 등록한다.** `POST /api/stocks/selection`이 검색 결과 하나를 받아 `stock` 행을
확보하고, 이후 모든 요청이 쓸 식별(시장·심볼·이름·통화)을 돌려준다.

- 국내·미국: 검색용 목록의 행으로 등록한다. 식별은 R6-6의 규칙을 따르고, **미국은 티커로 기존 행을
  먼저 찾는다**(FR-030a).
- 일본: 외부 검색 결과로 등록한다. 시장은 TSE, 통화는 JPY로 고정해 검증한다 — 클라이언트가 보낸 다른
  값은 거절한다.
- 시뮬레이션의 `require_stock`은 행이 없으면 **국내·미국에 한해** 검색용 목록으로 등록을 시도한다
  (이력에서 다시 실행하는 경로 — 이력은 브라우저에 있어 DB와 따로 산다). 시세 식별자에서 목록을 찾는
  규칙은 R6-6의 **역변환**이다. 역변환으로 찾지 못하거나 일본이면 "검색에서 다시 고르세요"로 답한다.

**Rationale**: 등록을 시뮬레이션 안에 숨기면 일본 종목은 이름을 알 길이 없고, 검색 결과와 등록된
종목이 어긋나도 사용자가 실행하기 전까지 모른다. 고르는 순간에 등록하면 실패가 그 자리에서 드러난다.

| 환율 수집 | 고쳐진 `ensure_background_job`(→ 003 시작 큐, 수집 표) 경유. 외환 화면과 같은 판정. 수집으로 채울 수 없는 구간은 수집하지 않음 (R6-10) |
| 원금 통화 | 서버 한 함수로 판정, EUR 제외 (R6-11) |
| 일본 검색 | 엔드포인트 분리, 응답 번호로 늦은 결과 폐기 (R6-12) |
| 원본 보존 | 지우지 않음, 같은 본문은 한 번만 저장 (R6-13) |
| 관측 | 수집 전용 로그, 비밀 정적 검사 확장 (R6-14) |
| 이용 조건 | 공식 API 개인 조회. 약관 사용자 확인 완료(2026-10-02), 비공개 저장소 (R6-15) |
| 종목 등록 | 고르는 순간 등록 — 005에 없던 경로 (R6-17) |
