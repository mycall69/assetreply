## R9-1. 실거래 출처와 응답 (FR-008, FR-019)

**실측** — 국토교통부 아파트 매매 실거래가 자료(`/1613000/RTMSDataSvcAptTrade/getRTMSDataSvcAptTrade`):

| 항목 | 결과 |
|------|------|
| 요청 | `serviceKey`(디코딩 키를 한 번만 퍼센트 인코딩), `LAWD_CD`(시·군·구 5자리), `DEAL_YMD`(계약 년월 6자리), `pageNo`, `numOfRows` |
| 응답 | 기본 XML(`application/xml`). `_type=json`이면 JSON — JSON은 `aptDong`·`dealDay`를 숫자로 바꾼다 |
| 쪽 크기 | `numOfRows=1000`·`9999` 모두 받는다. 송파구 94개월 중 한 달 최대 1,173건 → 2쪽 |
| 결과 | `header.resultCode`(정상 `000`), `body.totalCount`, `body.items.item[]` |
| 빈 결과 | 거래 없는 달, **틀린 `LAWD_CD`(99999)·틀린 `DEAL_YMD`(2024)·미래 달**이 모두 `000` + `totalCount 0` — 출처는 입력 오류를 알려 주지 않는다 |
| 필드 | `aptNm`, `aptDong`, `buildYear`, `buyerGbn`, `slerGbn`, `cdealType`(해제면 `O`), `cdealDay`(해제 신고일 `YY.MM.DD`), `dealAmount`(만원, 쉼표 문자열 `"120,000"`), `dealYear`·`dealMonth`·`dealDay`, `dealingGbn`(중개거래·직거래 — **2021-11 이전은 빈 값**), `estateAgentSggNm`, `excluUseAr`(전용㎡, **소수 0~4자리** — T001 실측), `floor`, `jibun`, `landLeaseholdGbn`, `rgstDate`, `sggCd`, `umdNm`(법정동명) |
| 시작 | 송파구는 **2005-12 계약분(3건)**부터 있고 2005-11 이전은 0건 — 2006년 실거래 신고제 시행 직전 계약분이다 |
| 한도 | 개발계정 **하루 10,000회**(포털 안내), 이용허락범위 **제한 없음** |
| 게이트웨이 오류 | 포털이 막으면 HTTP 403/400 + `OpenAPI_ServiceResponse.cmmMsgHeader`(`returnReasonCode` — 30 `SERVICE_KEY_IS_NOT_REGISTERED`, 12 `NO_OPENAPI_SERVICE`). 한도 초과는 22 `LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS`(포털 공통 코드) |

**Decision**:

- 실거래는 **상세 자료 API**(`/1613000/RTMSDataSvcAptTradeDev/getRTMSDataSvcAptTradeDev`)를 쓴다. 기본 자료와 같은 거래에 **단지 일련번호
  (`aptSeq`)·법정동 코드(`umdCd`)·본번·부번**이 더 있다(포털 안내). 단지를 이름이 아니라 출처의 식별자로 묶는다 — 이름이 바뀐 단지·같은 이름
  단지를 구별한다(FR-003). **지금 키는 상세 자료 API에 등록되어 있지 않다**(403 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`) — 사용자가 포털에서
  활용신청한다(T001, R9-3). → 2026-10-05 활용신청 반영, 아래 **상세 자료 실측**.
- 응답은 **XML**을 읽는다. JSON은 숫자처럼 보이는 문자열(`aptDong`, `jibun`)을 숫자로 바꿔 앞의 0을 잃을 수 있다.
- `numOfRows=1000`, `totalCount`만큼 쪽을 넘긴다. 받은 행 수가 `totalCount`와 다르면 형식 오류다(잘림 — 001·008과 같다).
- 금액은 쉼표를 지운 만원 정수 × 10,000 = 원 단위 정수(FR-019). 숫자가 아니면 그 응답 전체가 형식 오류다.
- 출처가 입력 오류를 0건으로 돌려주므로, `LAWD_CD`는 행정구역 표(R9-3)에 있는 코드만 보낸다. `DEAL_YMD`는 코드가 만든다.

**상세 자료 실측**(T001, 2026-10-05 — 송파구 2020-01~2023-09 46쪽 9,758행 등, `fixtures/apt/README.md`):

| 항목 | 결과 |
|------|------|
| 더한 필드 | `aptSeq`(단지 일련번호), `umdCd`(법정동 5자리 — 법정동 코드 = `sggCd + umdCd` 10자리), `bonbun`·`bubun`(4자리 0 채움 `0574`·`0000`), 도로명 필드 |
| `aptSeq` | `11710-8865`처럼 **시·군·구 코드가 앞에 붙는다** — 개편하면 단지 식별자가 바뀐다(옛 코드 요청은 0건, 새 코드 요청에 과거 거래가 새 `aptSeq`로 온다 — R9-3). 숫자 부분 1~4자리 |
| 빈 값 | **공백 한 칸**(`<aptDong> </aptDong>`) — 읽을 때 앞뒤 공백을 지운다. 빈 `items`는 `<items/>` |
| 지번 | `jibun`은 본번·부번에서 앞의 0을 지운 `본번` 또는 `본번-부번`과 9,758행 모두 같다 |
| 전용면적 | **소수 0~4자리**다 — 2자리 7,426행, 1자리 1,286, 3자리 750, 4자리 455(`143.7984`), 정수 152(`99`). 소수 2자리로 저장하면 반올림되어 경계(85㎡)·거래 키가 흔들린다 → `DECIMAL(9,4)`(R9-2) |
| 같은 키의 행 | 키 필드가 모두 같은 행이 45개월 중 31개월, 149행(순번 1 이상) — 순번(R9-4)이 없으면 잃는다 |
| 해제 | `cdealType = O` 328행 — 모두 `cdealDay`(`YY.MM.DD`)가 있다 |
| 거래 유형 | 2021-11 이전 계약은 모두 공백(6,556행), 뒤는 중개거래 3,044·직거래 158 |
| 층 | 받은 범위에 지하(음수) 층은 없다 — 출처 안내상 음수로 온다 |

**Alternatives considered**: 기본 자료 API(지금 키로 됨) — `aptSeq`가 없어 단지를 (법정동명, 지번, 단지명)으로 묶어야 한다. 이름이
바뀌면 갈라지고 재건축 전 단지와 지번이 같으면 섞인다. 상세 자료의 활용신청이 끝내 안 되면 이 방식으로 물러나고 그 한계를 화면에 적는다.

## R9-2. 평형 경계와 참조값 검증 (FR-004, FR-016, SC-003)

**실측**: 송파구 2019-01 ~ 2026-10 실거래 29,119건(95회 호출) 중 헬리오시티(가락동 913, 2018년 건축) 1,409건. 전용면적은 39.1·39.12·39.17·
39.86, 49.19·49.21·49.29·49.32, 59.96, 84.94~84.99, 99.6, 110.44·110.66, 130.06, 150.07·150.09㎡. 해제(`cdealType=O`) 56건, 거래 유형 빈 값
189건(2021-11 이전).

사용자 스프레드시트(45행, 날짜 열 없음)를 명세 FR-004의 경계표로 계산한 월별 평형별 건수·평균과 맞대었다:

| 계산 방식 | 맞는 위치 | 건수 일치 | 평균 일치 |
|-----------|-----------|-----------|-----------|
| 해제 **포함** | **2020-01 ~ 2023-09** | **225/225칸** | 원 단위 반올림 차이만(버림으로 계산한 칸이 1원 작다) |
| 해제 제외 | 같은 위치 | 200/225칸 | 187/225칸 — 그 기간 해제 27건 |

**Decision**:

- 평형 경계는 FR-004의 표 그대로다 — 39·49㎡ → 10평대, 59㎡ → 20평대, 84㎡ → 30평대(국평), 99.6㎡ → 30평대(대형), 110·130㎡ → 40평대,
  150㎡ → 50평대. 스프레드시트와 225칸 모두 같다.
- 스프레드시트는 **해제 거래를 넣고 평균을 반올림**한 값이다. 사용자 결정(2026-10-05): 화면은 해제를 **빼고**(FR-008), 평균은 **반올림**한다
  (FR-016). 참조값 테스트는 해제를 넣은 계산으로 스프레드시트와 대조하고(SC-003), 해제를 뺀 기대값은 같은 원본에서 따로 손계산한다.
- 전용면적은 **`DECIMAL(9,4)`**로 받은 자릿수 그대로 보관하고 경계 비교는 `Decimal`로 한다 — 84.99 같은 경계 근처 값이
  부동소수점으로 흔들리지 않게 한다. 출처가 소수 4자리까지 준다(R9-1 상세 자료 실측 — `143.7984`). 처음 정한 `DECIMAL(7,2)`는 반올림으로
  85㎡ 경계를 넘나들고(`85.0004` → `85.00`) 키 필드가 같아져 거래를 합칠 수 있어 바꿨다(T001 뒤, 푸시 전 마이그레이션 수정). 5자리 이상이
  오면 저장할 수 없으므로 그 응답은 형식 오류다(지어내지 않는다).

## R9-3. 행정구역·단지 목록의 출처 (FR-002, FR-003, FR-015)

**실측**:

| 출처 | 엔드포인트 | 지금 키 | 한도 |
|------|------------|---------|------|
| 행정안전부 법정동코드 | `/1741000/StanReginCd/getStanReginCdList` | ~~미등록~~ → 활용신청 뒤 정상(2026-10-05) | 10,000/일 |
| 국토교통부 공동주택 단지 목록 | `/1613000/AptListService4/getLegaldongAptList4` | 활용신청 뒤 정상(2026-10-05) — V3 이하는 폐기(사유 12) | 5,000/일 |
| 국토교통부 공동주택 기본 정보 | `/1613000/AptBasisInfoServiceV5/getAphusBassInfoV5` | 활용신청 뒤 정상(2026-10-05) — V4 이하는 폐기(사유 12) | 5,000/일 |

포털 안내의 필드: 법정동코드 — `region_cd`(10자리), `sido_cd`, `sgg_cd`, `umd_cd`, `ri_cd`, `locatadd_nm`(요청 `locatadd_nm`, `type=json`).
단지 목록 — `kaptCode`, `kaptName`, `bjdCode`(요청 `bjdCode` 10자리). 기본 정보 — `kaptdaCnt`(세대수), `kaptUsedate`(사용승인일), `kaptAddr`
(지번 주소), `bjdCode`(요청 `kaptCode`). 셋 다 이용허락범위 제한 없음.

**Decision**:

- **T001에서 사용자가 활용신청한다** — ① 아파트 매매 실거래가 상세 자료 ② 행정안전부 법정동코드 ③ 공동주택 단지 목록 ④ 공동주택 기본 정보.
  같은 계정이라 키(`DATA_API_KEY`)는 그대로다. 신청 뒤 각 API의 실제 응답을 픽스처로 받아 필드를 다시 확인한다(포털 안내와 다르면 이 절을
  고친다).
- **행정구역**: 법정동코드 API로 시·도 → 시·군·구 → 법정동을 만든다. 실거래 요청 단위는 시·군·구 5자리(`sido_cd + sgg_cd`)다. 일반시 아래
  구가 있는 곳(예: 수원시 41110 아래 장안구 41111)은 **구를 시·군·구로** 보이고 상위 시는 빼며, 화면 이름은 "수원시 장안구"로 붙인다. 리(`ri_cd ≠
  00`)는 빼고 법정동만 둔다. 목록은 처음 쓸 때와 그 뒤 30일(설정 `APT_LIST_REFRESH_DAYS`)마다 백그라운드로 다시 받는다(행정구역 개편 —
  예: 2026-07 인천 구 개편).
- **행정구역 개편 — 현존 코드만 쓴다**. 실측(2026-10-05, 기본 실거래 자료 8회): 출처는 **과거 거래도 새 코드로만** 준다 — 2020-01 계약분이
  춘천 옛 코드 `42110`(강원도)으로 0건, 새 코드 `51110`(강원특별자치도)으로 308건이고, 전주 완산 `45111`(전라북도) 0건, `52111`(전북특별자치도)
  449건이다(2025-01도 같다). 그래서:
  - 풀다운과 실거래 요청에는 현존 코드만 쓴다. 갱신에서 사라졌거나 출처가 폐지로 표시한 코드는 지우지 않고 `retired_at`을 남긴다(data-model 1절).
    사라진 코드를 요청하면 출처는 0건을 정상으로 준다 — "거래 없음"으로 보인다.
  - 개편 전에 옛 코드로 받은 거래는 개편 뒤 새 코드로 다시 받으면 같은 거래가 두 번 저장된다(거래 키에 시·군·구가 있다). 코드가 사라지면
    그 코드로 받은 거래를 `missing_since`로 집계에서 빼고 그 커버리지를 쓰지 않는다 — 새 코드의 수집이 전체 이력을 다시 받는다.
  - 상세 자료의 `aptSeq`에 시·군·구 코드가 들어가는지(개편 뒤 단지 식별자가 바뀌는지)는 T001에서 확인해 픽스처 README에 적는다. 바뀌면 개편
    뒤 단지가 새 단지로 보인다 — 재건축 연결과 같은 범위 밖의 한계다.
  - 단지 행의 시·군·구·법정동 코드는 새 코드로 받은 거래의 `aptSeq`로 갱신한다. 갱신 전(옛 코드로 남은 단지 — 이력의 다시 실행 등)에는 409
    `region_retired`로 "지역에서 다시 골라 실행"을 안내한다 — 받을 수 없는 옛 코드를 기다리거나 "거래 없음"으로 보이지 않게 한다.
  - 새 코드로 전체 이력을 다시 받으므로 확정 달도 출처의 최신 값으로 바뀔 수 있다 — 헌법 원칙 V의 확정 재현성 예외로 spec Assumptions에 적는다.
- **전국 목록 실측(T027, 2026-10-05)**: 1,000행씩 21쪽. 리 행 일부의 `locathigh_cd`가 공백 한 칸이다(15쪽의 `4777036039`·`4822025032`) —
  빈 상위 코드는 읽고 법정동이면 코드 앞 5자리의 시·군·구를 상위로 둔다. 세종특별자치시는 시·도 행이 없고 시·군·구 `3611000000` 하나뿐이다 —
  이름이 한 낱말인 시·군·구에서 시·도를 만든다. 시·도는 16곳이다(광주광역시·전라남도가 없고 전남광주통합특별시가 있다 — 지금 출처).
- **단지 목록(사용자 결정 Q1)**: 법정동을 고르면 단지 목록 API(1회)로 곧바로 이름을 보이고, 기본 정보 API(단지당 1회)로 세대수·사용승인
  연도를 백그라운드로 채운다(진행 스트림). 그 시·군·구의 실거래를 받으면 실거래의 단지(`aptSeq`)를 짝지어 더한다. 동의 단지 목록은 30일
  (`APT_LIST_REFRESH_DAYS`)이 지나 그 동을 처음 고를 때 다시 받는다 — 기본 정보는 새 단지만 받는다(세대수는 바뀌지 않는다).
- 같은 동에 이름이 같은 단지가 둘 이상이면 화면 항목 끝에 지번을 붙인다(FR-003) — "단지명 · 연도 · 세대"만으로는 둘이 같아 보인다.
- **짝짓기**: 단지 목록의 단지와 실거래의 단지는 법정동 코드(실거래 `sggCd + umdCd`, 목록 `bjdCode`)가 같고, 다음 중 하나면 같은 단지다 —
  ① 지번 본번·부번(실거래 `bonbun`·`bubun`, 목록 `kaptAddr`에서 추출)이 같다 ② 정규화한 단지명(공백·괄호와 그 안·"아파트" 제거)이 같고
  그 이름이 그 동의 **두 자료에서 하나씩뿐**이다. 큰 단지는 여러 필지에 걸쳐 자료마다 대표 지번이 다르다 — **헬리오시티는 단지 목록 주소가
  가락동 479, 실거래 지번이 913**이다(T001 실측, 2026-10-05). 지번만으로 짝지으면 헬리오시티가 두 번 보인다. 같은 동에 같은 이름 단지가
  여럿이면 이름으로 짝짓지 않는다(지번이 같아야 한다). 짝짓지 못하면 따로 보인다(가구수 없음) — 다른 단지를 하나로 합치는 것보다 덜
  위험하다. 짝짓기 규칙과 실패율은 송파구 픽스처로 테스트한다.
  - **재건축 전후는 짝짓지 않는다**(T027 실측, 2026-10-05): ①·② 모두 **실거래 건축년도와 사용승인 연도를 둘 다 알고 10년 넘게 다르면**
    짝짓지 않는다. 강남구 개포동 개포자이프레지던스(목록 주소 189, 2023 사용승인)가 같은 필지의 옛 단지 개포주공4단지(실거래 `11680-289`,
    지번 189, 거래 2006-01~2023-01)와 지번으로 짝지어지고, 새 단지의 거래(`11680-5235`, 지번 1284)는 따로 남았다 — 재건축 전후 연결은 범위
    밖이다(spec). 재건축은 준공 30년이 지나야 하므로 차이가 수십 년이고, 가락동 짝 22개의 차이는 0년(21개)·3년(가락현대5차 1개)이다.
    한쪽 연도를 모르면 이 조건을 보지 않는다. 실거래 쪽 연도는 그 실행에서 본 건축년도, 없으면 단지 행의 `move_in_year`(`move_in_source =
    trade`)다.
- **단지 id는 바뀌지 않는다** — 이력이 단지 id를 저장한다(FR-032). 짝짓기는 있는 행에 다른 쪽 식별자를 붙이는 것으로 한다. 두 행이 이미 따로
  있을 때 짝이 드러나면(예: 지번을 나중에 읽음) 먼저 만든 행에 합치고 다른 행은 지우지 않고 `merged_into`를 남긴다 — 옛 id로 열어도 같은
  단지다(data-model 2절).
- **세대수**는 기본 정보의 `kaptdaCnt`(JSON 실수 — `9510.0`)다. **0.0인 단지가 있다**(신축 더샵송파루미스타 — `hoCnt 183`) — 0이면
  호수 `hoCnt`를 쓰고, 그것도 0이면 모른다(`None` — 지어내지 않는다, FR-003).
- 입주년도는 기본 정보의 사용승인일 연도, 없으면 실거래의 `buildYear`다. 어느 쪽에서 얻었는지(`move_in_source`)를 남긴다(헌법 원칙 V).

**Alternatives considered**: 법정동코드 전체 자료 파일을 저장소에 넣기 — 개편을 따라가지 못한다. 실거래만으로 단지 목록 만들기 — 시·군·구
전체 이력(약 280회)을 받을 때까지 단지를 못 고른다(사용자 결정 Q1에서 기각). 단지 목록 자료만 — 의무관리 대상이 아닌 작은 단지가 빠진다.

## R9-4. 거래의 고유 키와 멱등 저장 (FR-009, 헌법 원칙 V)

**실측**: 송파구 29,119건 중 (시군구·법정동·지번·단지·동·층·면적·계약일·금액)이 모두 같은 거래가 **232쌍**이고 229쌍이 같은 응답 안에 있다 —
같은 날 같은 층·같은 면적·같은 금액으로 다른 호가 거래된 것이다(예: 현진타워 7층 2020-02-29 2억 8천 2건). 같은 거래가 두 계약 월의 응답에
나온 적은 없다.

**Decision**:

- 거래 키 = (`lawd_cd`, `deal_date`, `apt_seq`, `apt_dong`, `floor`, `excl_area`, `amount`, **`occurrence`**) — `occurrence`는 한 계약 월의 응답(쪽을 차례로
  이은 것) 안에서 앞 필드가 모두 같은 행의 순번(0부터)이다 — 2쪽짜리 달도 순번이 쪽을 건너 이어진다. 같은 계약 월을 다시 받으면 같은 순번이 같은 행에 돌아간다(같은 값의 행은 서로 바꿔도 집계가 같다).
- 바뀔 수 있는 필드(`cdealType`·`cdealDay`·`dealingGbn`·`rgstDate`·`estateAgentSggNm`)는 키에 넣지 않고 upsert로 고친다 — 해제가 나중에 붙으면
  같은 행이 해제로 바뀐다.
- 헌법 원칙 V의 "(자산 식별자, 날짜) 복합 유니크 키"는 **비정기 거래**에서 (단지, 계약일)만으로 유일하지 않다 — 거래를 가르는 필드와 순번을
  더한다. 일별 시계열의 불변식을 거래 사건에 맞춘 것이고 Complexity Tracking에 기록한다(plan).
- 다시 받은 응답에서 사라진 거래(출처가 지운 행)는 지우지 않고 `missing_since`로 표시하고 집계에서 뺀다 — 원본에 근거가 남는다.

## R9-5. 수집 단위·잠정·한도 (FR-009~FR-012, 사용자 결정 Q3)

**Decision**:

- **수집 단위는 시·군·구 × 계약 월**이다. 단지를 고르면 그 시·군·구의 **전체 이력**(첫 달 ~ 이번 달)을 받는다 — 시작 가능 날짜(FR-005)와
  36개월 창(FR-016)이 단지·평형의 모든 거래를 요구한다. 송파구 기준 약 250개월 × 1~2쪽 ≈ 280회.
- **첫 달은 발견한다**(헌법 — 기준 시작일은 상수가 아니다): 설정 `APT_TRADE_PROBE_START`(기본 `2005-01`)부터 받고, 처음으로 거래가 있는
  달을 그 시·군·구의 첫 달로 기록한다.
- **해제는 늦게 들어온다**(분석 단계 실측 — 송파구 2019-01~2026-10 기본 자료, 해제 신고일이 있는 해제 840건). 계약 달로부터 해제 신고 달까지:

  | 계약 달 기준 | 건수 | 누적 |
  |--------------|------|------|
  | 같은 달 | 175 | 20.8% |
  | +1 | 270 | 53.0% |
  | +2 | 185 | **75.0%** |
  | +3 | 109 | 88.0% |
  | +4 ~ +5 | 62 | 95.4% |
  | +6 ~ +11 | 29 | **98.8%** |
  | +12 이상 | 10 | 100% (가장 늦게 +35) |

  최근 달은 늦은 해제가 아직 덜 쌓였으므로 실제 비율은 표보다 늦은 쪽이다. 잠정 3개월(같은 달 ~ +2)만 다시 받으면 해제의 4분의 1이 확정 달에
  남아 시세에 영구히 들어간다(FR-008·SC-006 위반).
- **잠정 기간 = 최근 12개월**(설정 `APT_TRADE_PROVISIONAL_MONTHS`, 기본 12 — 사용자 결정 2026-10-05, 분석 뒤). 다시 받는 빈도는 둘이다:
  최근 3개월(설정 `APT_TRADE_DAILY_RECHECK_MONTHS`, 기본 3)은 **하루 한 번**(한국 시간 — 신고가 더 들어온다), 4~12개월 전 달은 **한 달에 한 번**
  (그 달 처음 확인할 때 — 해제가 늦게 들어온다). 시·군·구당 하루 3~4회 + 한 달 9~10회. 잠정 기간을 벗어난 달은 확정이고 다시 받지 않는다 —
  그 뒤의 해제(약 1.2%)는 반영하지 않는 한계로 둔다(spec Assumptions).
  - 기각: 잠정 3개월 유지(해제의 75%만 반영), 잠정 36개월(거의 100% — 한 달 33회로 비용 대비 이득이 작다).
- **하루 한도**: 출처마다 하루 호출 수를 DB에 센다(한국 시간 날짜 기준). 설정 `DATA_API_DAILY_LIMIT_TRADE`(기본 9,000 — 포털 10,000에서 여유)·
  `DATA_API_DAILY_LIMIT_KAPT`(기본 4,500)·`DATA_API_DAILY_LIMIT_REGION`(기본 9,000)에 닿으면 그 수집을 **한도 초과**로 멈추고 받은 달까지는
  커버리지에 남긴다. 다음 날·다시 실행에서 이어 받는다(SC-012). 하루 한도 기준으로 시·군·구 30곳 남짓의 전체 이력을 받을 수 있다.
- 동시 요청 수는 설정 `DATA_API_MAX_CONCURRENT`(기본 3)로 공공데이터포털 출처 전체가 함께 지킨다(008의 ECOS 관문과 같은 방식 —
  `DataGoKrGate`). 실패(연결·HTTP 5xx)는 지수 백오프 + 지터로 다시 시도한다 — 횟수 `DATA_API_RETRY_MAX_ATTEMPTS`(기본 4), 지연
  `DATA_API_RETRY_BASE_DELAY_MS`(기본 1000) × 2ⁿ(헌법 원칙 II — 재시도 정책은 설정). 인증 실패는 다시 시도하지 않고, 게이트웨이 사유 22면
  한도 초과로 즉시 멈춘다.
- **처음 고르는 시·군·구는 전체 이력을 받는다**(약 280회) — 하루 한도 9,000회로 30곳 남짓이다. 화면(E2)과 README에 안내한다.
- **원본 중복**: 송파구 95개월 원본이 약 15MB다(실측 — 시·군·구 전체 이력은 수십 MB). 다시 받기의 대부분은 본문이 같으므로 같은 요청의 마지막
  원본과 본문 해시가 같으면 새 행을 만들지 않는다(data-model 4절). 내용이 다른 판은 모두 남아 잠정→확정 변화를 추적할 수 있다(헌법 원칙 V).
- **실패 종류**(FR-014): 인증(게이트웨이 사유 20·30·31·32), 한도(22·자체 한도), 형식(`resultCode ≠ 000`, 잘림, 읽을 수 없는 금액·면적,
  게이트웨이 사유 12), 연결(HTTP 오류·시간 초과·XML이 아님). 008의 문구·할 일 규칙을 따른다.
- 수집 줄은 다른 자산군과 **따로**다(lifespan 태스크 하나 추가 — 8개). 그 태스크 안에서 실거래 줄과 목록 줄(행정구역·단지 기본 정보)로 나뉜다 —
  006 목록 갱신 워커가 국내·미국으로 나뉜 것과 같다. 두 줄은 같은 출처 관문을 함께 지킨다.

## R9-6. 시세 창 계산 (FR-016~FR-018)

**Decision**:

- 그 달 평균 = 그 달(계약일 기준 달력 월) 같은 단지·같은 평형 구분의 **해제·사라짐이 아닌** 거래 금액 합 ÷ 건수, 원 미만 **반올림**
  (`ROUND_HALF_UP`, 사용자 결정 2026-10-05).
- 적용 시세 = 창 [1, 3, 6, 12, 24, 36]개월 중 거래가 있는 가장 짧은 창의 평균(창 안 모든 거래의 평균 — 달별 평균의 평균이 아니다). 창은 기준
  달을 끝으로 거꾸로 센다(기준 달 포함). 36개월 안에 없으면 시세 없음.
- 1개월 창 = 실측, 더 넓은 창 = **추정**. 창 안에 잠정 달(최근 12개월)이 있으면 **잠정**. 추정·잠정은 계산 결과에만 있고 저장하지 않는다.
- 순수 함수(`simulation/apt_price.py`) — 거래 목록과 기준 달을 받아 (시세, 창, 건수, 추정, 잠정)을 돌려준다.

## R9-7. 비용·세금 계산과 세법 표 (FR-020~FR-024, 사용자 결정 2026-10-05)

**Decision**:

- 세법은 **시행일별 표**로 둔다(`simulation/apt_tax_rules.py` — 계산 로직이 없는 데이터 모듈. 항목마다 근거 법령·조문·시행일을 적는다).
  계산 함수(`simulation/apt_tax.py`)는 표와 금액·날짜를 받아 세액을 돌려주는 순수 함수다(헌법 원칙 IV·VI).
- 적용 시점: 취득세·중개 보수는 **매입일**, 재산세·종부세는 그해 **과세기준일(6월 1일)**에 시행 중인 표.
- 표 범위: **2006-01-01부터** 오늘까지(실거래 신고제·실거래가 과세 시행 — R9-1). 표가 덮지 않는 날짜면 계산하지 않고 그 사실을 보인다(FR-023 —
  가까운 해로 대신하지 않는다). 출처는 2005-12 계약분부터 주므로 **시작 가능 날짜 = 첫 거래 달 1일과 2006-01-01 중 늦은 날**이다(FR-005) —
  2005-12 거래는 시세 창에는 쓰고 매입일로는 고를 수 없다.
- 보유세의 기준 시세(그해 6월)가 추정·잠정이면 세금에 그 기준(달·시세·창·건수·추정·잠정)을 함께 싣는다 — 세금이 추정 시세에서 나왔다는
  사실이 드러나야 한다(헌법 원칙 V, FR-021).
- 보유세 기준 금액 = 그해 6월의 적용 시세 × 보유세 기준 비율(기본 60%) = **공시가격 대용**(사용자 결정). 과세표준 = 기준 금액 × 그해
  공정시장가액비율(재산세·종부세 각각). 6월 시세가 없으면 그해 보유세를 계산하지 못한다 — 0으로 두지 않고 "YYYY년 보유세 계산 불가(6월 시세
  없음) — 비용이 실제보다 작다"를 보드와 그해 행에 보인다.
- 세목:
  - **취득세**: 1세대 1주택 유상취득 본세 + 지방교육세 + 농어촌특별세(전용 85㎡ 초과). 과세표준 = 매입가.
  - **중개 보수**: 매입가 × 그때의 법정 상한 요율(구간별 한도액 포함), 부가세 없음(Assumptions).
  - **재산세**: 과세표준 × 세율(구간 누진, 1세대 1주택 특례가 있는 해는 특례 세율) + 지방교육세(재산세의 20%) + 도시지역분(과세표준의 0.14%).
    7월·9월에 반씩, 세액이 그해 일괄 기준 이하면 7월에 전부. 공동 소유여도 주택 하나의 세액이다.
  - **종합부동산세(부부 5:5)**: 1인당 기준 금액 = 기준 금액 ÷ 2. 1인당 과세표준 = (1인당 기준 금액 − 그해 1인당 공제) × 그해 공정시장가액비율
    (음수면 0). 세액 = 과세표준 × 세율(누진) − 재산세 중복분(그해 법정 산식) + 농어촌특별세(20%). 두 사람 합. 1세대 1주택(공동명의 각자 공제)·
    고령자·장기보유 공제·세부담 상한 없음.
  - 끝수: 세목마다 10원 미만 버림(FR-024).
- **표의 시기 구분(설계용 개요 — 확정 값은 R9-7a. 아래 개요의 2005~2008 재산세·종부세 서술은 R9-7a가 바로잡았다)**:

## R9-8. 매입·보유 계산 (FR-005, FR-006, FR-025~FR-027, 사용자 결정 Q4)

**Decision**:

- 매입가 = 직접 넣은 금액, 없으면 매입 달의 적용 시세(추정이면 그 사실을 보인다). 둘 다 없으면 409(`no_price_at_purchase`).
- 시작 가능 날짜 = 그 단지·평형 구분의 첫 거래 달 1일(해제 제외)과 세법 표의 첫 날(2006-01-01) 중 늦은 날(R9-7). 그보다 이르면
  409(`before_first_trade`) + 시작 가능 날짜 + 근거(`first_trade` · `tax_rules`).
- 매달 행: 매입 달 ~ 이번 달. 평가액 = 그 달 적용 시세(없으면 비움). 누적 비용 = 취득 비용 + 그 달까지 납부한 보유세. 투자 수익 = 평가액 −
  매입가 − 누적 비용. 수익률 = 투자 수익 ÷ (매입가 + 취득 비용), 소수 6자리 짝수 반올림(기존 `quantize_rate`).
- 보유세 납부: 과세기준일(6월 1일)에 소유(매입일 ≤ 그해 6월 1일)한 해마다 7월·9월(재산세)·12월(종부세). 매입 연도의 6월 1일 뒤에 샀으면
  그해는 없다. 이번 달까지 납부 달이 오지 않은 세금은 넣지 않는다.
- 순수 함수(`simulation/apt_holding.py`)가 거래·매입 조건·세법 표·설정을 받아 행과 요약을 만든다.

## R9-9. 계약 테스트 픽스처 (헌법 원칙 III)

**Decision**: T001에서 실제 응답을 받아 `backend/tests/contract/fixtures/apt/`에 둔다 — 상세 자료(송파구 2020-01 ~ 2023-09, 헬리오시티 참조값
대조용 — 45개월, 그리고 해제가 있는 달·2쪽짜리 달), 기본 정보·단지 목록(가락동), 법정동코드(서울특별시 송파구 일부), 게이트웨이 오류(사유 30),
빈 결과. 응답 본문만 저장하고 요청 URL(키 포함)은 저장하지 않는다. 받은 날짜와 범위를 `README.md`에 적는다.

## R9-10. 화면 (FR-001~FR-007, FR-028~FR-034)

**Decision**:

- 경로 `/realestate`(사이드바 "부동산", 상단 바 제목 "부동산" — 008에서 고친 제목 표·사이드바 가드 테스트가 함께 잡는다). 미구현 가드
  (`noUnbuiltAssetRoutes.test.ts`)의 `realestate`를 뺀다.
- 행정구역 풀다운 셋(시·도 → 시·군·구 → 법정동) + 단지 풀다운("헬리오시티 · 2018년 입주 · 9,510세대") + 평형 일곱(거래 없는 구분은 비활성,
  경계는 툴팁) + 매입일 + 매입가(선택, 쉼표) + 시뮬레이션.
- 보드는 `PerformanceBoard`의 칸 구성과 달라(매입가·투입 금액·누적 보유세·평가액·수익·수익률) 부동산 전용 보드를 둔다 — 공유 보드에 칸을
  늘리면 다른 자산군 테스트가 흔들린다.
- 차트는 `PerformanceChart`를 쓰고 시계열 응답에 `gaps`(시세 없음 = 끊음)와 점별 `estimated`·`provisional`을 싣는다. 끊기는 이유 `no_price`를
  더한다(기존 `not_collected`·`source_missing`처럼 끊는다).
- 비교는 `ComparisonChart` 그대로. 이력 키 `assetreplay:realestate-history:v1`(기존 형식 — 008 data-model의 규칙).

## R9-11. 성능 (SC-001, SC-002)

**Decision**: 단지의 거래는 많아야 수천 건(헬리오시티 7년 1,409건) — 요청마다 DB에서 읽어 계산해도 3초 안이다. 결과를 저장하지 않는다(설정·
세법·잠정 거래가 바뀌면 달라진다). 수집 진행은 시·군·구 작업의 SSE(받은 달 / 받을 달)로 2초 안에 보인다.
