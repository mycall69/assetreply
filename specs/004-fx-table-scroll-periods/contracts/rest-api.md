# Contract: REST — 004

**Feature**: 004-fx-table-scroll-periods | **Date**: 2026-09-27

001~003이 정의한 엔드포인트는 그대로 둔다. 이 문서는 **`GET /api/fx/daily`의 확장분만**
다룬다. 새 엔드포인트를 만들지 않는다.

모든 금액·비율은 JSON **문자열**이다. `number`는 IEEE 754라 `Decimal` 정밀도가 손실되며,
이는 헌법 원칙 VI를 API 경계에서 무력화한다(001이 세운 규약).

## `GET /api/fx/daily` — 기간 단위 매개변수 추가

**새 엔드포인트를 만들지 않는 이유**: 바뀌는 것은 "행을 고르는 기준"뿐이고 응답의 의미는
같다. 경로를 나누면 002의 화면과 004의 화면이 서로 다른 계약을 보게 되어, 시간이 지나며
파생 환율 규칙이나 잠정 표시가 한쪽에만 반영될 수 있다.

### 질의 매개변수

| 이름 | 필수 | 기본 | 설명 |
|------|------|------|------|
| `currency` | 예 | — | 통화 코드 |
| `period` | 아니오 | `daily` | `daily` · `weekly` · `monthly` (FR-006, FR-007) |
| `before` | 아니오 | — | 이 날짜 **미만**만 반환. 주·월 단위에서는 **기준일** 기준 |
| `limit` | 아니오 | 30 | 1~200 |

`period`의 기본값이 `daily`인 것이 FR-007의 계약상 표현이다. 매개변수를 생략하면 002와
**완전히 같은 응답**이 나온다 — 기존 호출자가 깨지지 않는다.

### 응답

```json
{
  "currency": "USD",
  "period": "weekly",
  "quoteUnit": 1,
  "appliedSpread": { "cashBuy": "0.001800", "cashSell": "0.001800",
                     "remitSend": "0.000500", "remitReceive": "0.000500" },
  "spreadBasis": "current",
  "rows": [
    {
      "date": "2026-09-23",
      "baseRate": "1360.000000",
      "isProvisional": false,
      "derived": { "cashBuy": "1362.45", "cashSell": "1357.55",
                   "remitSend": "1360.68", "remitReceive": "1359.32" },
      "periodFrom": "2026-09-21",
      "periodTo": "2026-09-27",
      "shiftedFrom": "2026-09-25",
      "isOngoing": true
    }
  ],
  "hasMore": true,
  "oldestReturned": "2026-09-23"
}
```

### 002에서 더해지는 필드

| 필드 | 의미 | 근거 |
|------|------|------|
| `period` | 이 응답이 어느 단위인지 | 화면이 도착한 응답의 단위를 현재 선택과 대조해 거른다 (FR-011) |
| `periodFrom`·`periodTo` | 이 행이 덮는 구간 | 선택 날짜가 어느 행에 속하는지 **화면이** 판정한다 (FR-019, research R4-7) |
| `shiftedFrom` | 원래 기준일. 옮겨지지 않았으면 **키 자체가 없다** | FR-013 |
| `isOngoing` | 구간이 아직 끝나지 않았는가 | FR-015a |

### `shiftedFrom`은 키를 생략한다

002·003이 세운 규약을 잇는다 — **정상 상태에 값을 두면 화면이 존재 여부가 아니라 내용을
검사해야 한다.** 옮겨지지 않은 행에는 이 키가 없다(FR-014).

반대로 `isOngoing`은 항상 `false`/`true`를 명시한다. 이것은 "확인했고 아니다"와 "확인하지
않았다"가 구별되어야 하는 값이다.

### 세 표시는 각각 따로 실린다

`shiftedFrom`·`isOngoing`·`isProvisional`은 **동시에 참일 수 있다**(FR-015b). 위 예시가
그 경우다 — 2026-09-23(수)이 이번 주의 마지막 고시일이고, 금요일(09-25)이 아니라 옮겨졌고,
이번 주가 아직 안 끝났다.

서버가 하나로 합쳐 보내면 화면이 되돌릴 수 없으므로 합치지 않는다.

### 일 단위의 응답

`period=daily`면 `periodFrom == periodTo == date`이고, `shiftedFrom`은 없고,
`isOngoing`은 `false`다.

**필드를 빼지 않는다.** 단위에 따라 응답 구조가 달라지면 화면이 두 형태를 다뤄야 한다.

## 수집 중 응답 — 변경 없음

001·002가 정한 `202 collecting` 응답을 그대로 유지한다. 미수집 구간이 있으면 기간 단위와
무관하게 같은 형태로 돌려준다.

```json
{ "status": "collecting", "currency": "USD", "jobId": 42,
  "missingDays": 12, "progressUrl": "/api/fx/progress?jobId=42" }
```

## 오류

001의 공통 오류표를 따른다. 이번 기능이 더하는 것은 하나다.

| 상황 | 상태 | `status` |
|------|------|----------|
| 지원하지 않는 통화 | 404 | `unknown_currency` |
| **알 수 없는 `period` 값** | 400 | `invalid_query` |
| `limit` 범위 밖 | 422 | (FastAPI 기본 검증) |

`period`에 알 수 없는 값이 오면 **조용히 `daily`로 떨어뜨리지 않는다.** 화면이 잘못된 값을
보냈는데 정상 응답이 오면 그 버그가 드러나지 않는다.

## 내려받기

**별도 엔드포인트를 만들지 않는다.** 화면이 이미 받은 행으로 파일을 만든다 (research R4-5).

002의 CSV 생성이 행 객체를 받아 문자열로 만드는데, 그 행에 이미 네 값(`shiftedFrom`,
`isOngoing`, `periodFrom`, `periodTo`)이 있으므로 열을 더하면 된다.

| 열 | 내용 |
|----|------|
| 기존 열 | 002가 정한 그대로 (날짜, 매매기준율, 파생 4종) |
| 기간 단위 | 파일 머리말 또는 열로 — 어느 단위인지 파일만 봐도 알아야 한다 (FR-016a) |
| 원래 기준일 | 옮겨졌을 때만 값이 있다 (FR-016b) |
| 진행 중 | 참/거짓 (FR-016b) |

**FR-016b가 이 표의 이유다.** 표시가 파일에서 빠지면 파일만 본 사람은 그 날짜를 금요일·말일
값으로 읽는다 — 화면에서 막은 오해가 파일에서 되살아난다.
