# Phase 0 Research: 외환 분석 화면 통합과 전역 내비게이션 셸

**Feature**: 002-fx-analysis-workspace | **Date**: 2026-08-30

001의 설계 결정(R1~R13)은 그대로 유효하다. 여기서는 이번 기능이 새로 만드는 결정만 다룬다.
번호는 001과 겹치지 않도록 `R2-`를 접두한다.

---

## R2-1. 확정/잠정 상태의 표현

**Decision**: `fx_rate`에 `is_provisional BOOLEAN NOT NULL DEFAULT FALSE` 한 컬럼을 더한다.
별도 테이블을 만들지 않는다.

**Rationale**: 명세 단계에서 "시계열에 저장하되 확정/잠정 구분을 함께 둔다"로 정해졌다
(Clarifications). 단일 컬럼이면 기존 기본 키 `(currency_code, quote_date)`와 upsert 헬퍼,
인덱스가 그대로 성립하고 조회 경로가 하나로 유지된다. 헌법 v5.0.0 원칙 V가 요구하는
"확정값과 구분 없이 저장하지 말 것"은 컬럼 하나로 충족된다.

불리언을 택하고 상태 열거형을 두지 않은 이유는 현재 필요한 구분이 둘뿐이기 때문이다
(원칙 IX, YAGNI). "정정 대기" 같은 중간 상태가 실제로 필요해지면 그때 확장한다.

**Alternatives considered**:
- **별도 테이블 `fx_provisional_rate`** → 확정 시계열을 완전히 격리하지만 조회마다 두
  저장소를 합쳐야 한다. 차트·표·내려받기가 모두 합집합을 다뤄야 해 코드 경로가 두 배가 된다. 기각.
- **원본 응답 기록만으로 판단** → 저장 구조를 바꾸지 않아도 되지만, 조회 때마다 원본을 뒤져
  확정 여부를 계산해야 한다. 조회 성능과 단순성 모두 손해. 기각.
- **상태 열거형(`confirmed`/`provisional`/`corrected`)** → 확장성은 좋으나 지금 쓰이지 않는
  값을 만든다. 기각.

## R2-2. 잠정 레코드와 수집 커버리지의 관계

**Decision**: `fx_coverage.covered_through`는 **확정 수집만** 반영한다. 잠정 레코드가
존재해도 커버리지는 전진하지 않는다.

**Rationale**: 이것이 이번 기능에서 가장 조용한 함정이다. 001의 재개 로직
(`next_start_date`)은 `covered_through + 1`부터 다시 받는다. 오늘 잠정 행을 저장하면서
커버리지를 오늘까지 밀어버리면, 다음 증분 수집이 오늘을 건너뛴다. 그러면 **잠정값이 영원히
확정값으로 대체되지 않는다.** 화면은 확정 표시로 바뀌지도 않고, 값이 정정돼도 반영되지 않는다.

커버리지를 어제 이하로 유지하면 다음 증분 수집이 자연히 그 날짜를 다시 받아오고, R2-3의
확정 전환이 별도 장치 없이 성립한다. 명세의 FR-037b가 이 규칙을 요구사항으로 못박고 있다.

**Alternatives considered**:
- **커버리지를 오늘까지 확장하고 잠정 여부를 별도 플래그로 관리** → 커버리지 의미가 "수집을
  시도한 범위"와 "확정된 범위" 둘로 갈라진다. 001의 영업일 판정(R8: 커버리지 안에 값이 없으면
  고시 없는 날)이 오늘에 대해 잘못된 답을 낸다. 기각.
- **잠정 저장 시 커버리지를 건드리지 않되 별도 `provisional_through` 컬럼 추가** → 아무도 읽지
  않는 컬럼이 생긴다. 오늘 잠정 행의 존재 자체가 이미 그 정보다. 기각.

## R2-3. 잠정에서 확정으로의 전환 경로

**Decision**: 별도 전환 작업을 만들지 않는다. 날짜가 지나면 기존 증분 수집이 그 날짜를
받아오고, upsert가 값을 덮으면서 `is_provisional`을 `FALSE`로 기록한다.

**Rationale**: 명세 단계에서 "값을 다시 받지 않고 상태만 바꾸지 않는다"로 정해졌다.
출처가 마감 후 값을 정정했을 수 있으므로, 확인 없이 상태만 뒤집으면 틀린 값이 재현성 보장
구간으로 들어간다(헌법 원칙 V).

R2-2에서 커버리지를 전진시키지 않기로 했으므로 증분 수집이 자동으로 그 날짜를 포함한다.
새 스케줄러도, 배치 작업도 필요 없다.

**전환 추적(FR-043)**: 001이 모든 원본 응답을 기한 없이 보관한다(FR-004a). 잠정 시점 응답과
확정 시점 응답이 모두 남으므로 값의 변화를 사후에 대조할 수 있다. 전환 시각은 그 행의
`updated_at`이다. 별도 이력 테이블을 만들지 않는다.

**Alternatives considered**:
- **자정에 도는 배치로 상태만 전환** → 값을 재확인하지 않아 정정을 놓친다. 원칙 V 위반. 기각.
- **조회 시점에 잠정 레코드를 발견하면 즉시 재수집** → 조회 응답 시간이 외부 호출에 묶인다.
  SC-009a(3초)를 외부 API 상태에 인질로 잡히게 한다. 기각.

## R2-4. 차트에서 잠정 포인트의 보존

**Decision**: 별도 장치를 추가하지 않는다. 현재 LTTB 구현이 이미 요건을 만족한다.

**Rationale**: FR-017b는 "표시 점 수를 줄이는 처리를 적용하더라도 구간의 가장 최근 값은 항상
표시되어야 한다"를 요구한다. 001의 `simulation/downsample.py`를 확인한 결과 LTTB는 첫 점과
끝 점을 항상 결과에 포함한다(`result = [points[0]]` … `result.append(points[-1])`). 오늘
잠정값은 구간의 마지막 점이므로 다운샘플링에서 탈락하지 않는다.

**다만 이 성질에 테스트가 없다.** 알고리즘의 우연한 성질에 요구사항을 맡기면, 나중에
다운샘플링을 교체할 때 조용히 깨진다. 끝점 보존을 명시적으로 검증하는 테스트를 추가한다.

**Alternatives considered**:
- **마지막 점을 다운샘플링 대상에서 제외하고 별도로 덧붙이기** → 현재 구현에서 불필요하고,
  중복 추가로 마지막 점이 두 번 들어갈 위험이 있다. 기각.
- **잠정 포인트를 별도 시리즈로 렌더링** → 차트 라이브러리에서 두 시리즈의 연결이 끊겨
  선이 이어지지 않는다. 시각적 구분은 마지막 구간의 스타일로 처리한다. 기각.

## R2-5. 파생 환율의 산출 위치

**Decision**: **서버**가 산출해 문자열로 내려준다. 표 전용 엔드포인트 `GET /api/fx/daily`가
날짜별 매매기준율과 파생 환율 4종을 함께 반환한다.

**Rationale**: 헌법 원칙 VI가 결정한다. 표는 30행 × 4종 = 120개의 파생값을 요구하는데,
브라우저에는 `Decimal`이 없다. 클라이언트에서 계산하면 곧 IEEE 754 부동소수점 연산이고,
이는 원칙 VI를 API 경계에서 무력화한다. 001이 이미 같은 이유로 "금액·비율은 문자열로 수신하고
문자열로 유지한다"를 `apiClient.ts`에 못박아 두었다.

서버 산출은 001의 `simulation/spread_calc.py` 순수 함수를 그대로 재사용한다. 단일 날짜 조회와
표가 같은 함수를 쓰므로 같은 입력에 다른 결과가 나올 수 없다(FR-023, FR-027).

**Alternatives considered**:
- **클라이언트에서 계산** → 원칙 VI 위반. 30년 복리가 아니라 단순 곱셈이라 오차가 작다는
  반론이 가능하지만, 원칙은 "금융 계산에 `float` 금지"이지 "오차가 클 때만 금지"가 아니다. 기각.
- **기존 `GET /api/fx/series`에 파생을 얹기** → 차트는 파생이 필요 없고 최대 2000점을
  내려보낸다. 여기에 4종을 더하면 응답이 5배가 되고 SC-009a(3초)에 불리하다. 용도가 다른
  두 소비자를 한 엔드포인트에 묶지 않는다. 기각.
- **JSON `number`로 전달하고 표시 직전 반올림** → 전달 단계에서 이미 정밀도가 손실된다. 기각.

## R2-6. 첫 진입 시 데이터 로딩 전략

**Decision**: 화면 진입 시 **네 번의 병렬 호출**로 가져온다 — 요약·차트·표, 그리고 통화별
축적 범위(`GET /api/fx/coverage`). 하나의 집계 엔드포인트로 묶지 않는다.

**Rationale**: 세 영역은 갱신 주기와 조건이 다르다. 기간 프리셋을 바꾸면 차트만, 스프레드를
바꾸면 요약과 표만, 새로고침하면 요약과 표의 첫 행만 다시 필요하다. 집계 엔드포인트로 묶으면
어느 하나가 바뀔 때마다 전부를 다시 받아야 하고, SC-005(스프레드 변경 후 2초)가 가장 무거운
차트에 발목을 잡힌다.

병렬 호출은 가장 느린 하나가 전체 시간을 정하므로 SC-009a(3초) 판정도 단순해진다.

**커버리지를 함께 받는 이유**: 선택 날짜가 조회 가능 범위 안인지 판정하려면 통화별
`coveredFrom`·`coveredThrough`가 필요하다(FR-010). 선택 날짜를 바꿀 때마다 서버에 묻는 대신
진입 시 한 번 받아 두고 클라이언트가 판정한다 — 날짜를 옮길 때마다 왕복이 생기면
SC-009(차트 조작 1초)를 만족할 수 없다. 같은 응답이 기간 프리셋 "전체"의 범위 산정에도
쓰인다(FR-019). 세 통화를 한 번에 반환하므로 통화 변경 시 재요청이 없다.

**Alternatives considered**:
- **단일 집계 엔드포인트** → 왕복 1회로 줄지만 부분 갱신이 불가능해진다. 기각.
- **차트를 지연 로딩(요약·표 먼저)** → 체감 속도는 좋으나 명세가 "모든 구성 요소 3초"로
  정해졌으므로(Clarifications) 단계를 나눌 이유가 없다. 필요해지면 그때 도입한다. 기각.

## R2-7. CSV 생성 위치

**Decision**: 브라우저에서 생성한다. 서버가 이미 문자열로 내려준 값을 **파싱하지 않고**
그대로 조립한다.

**Rationale**: 표에 그릴 값을 이미 받아 두었으므로 서버를 한 번 더 부를 이유가 없다(원칙 IX).
정밀도 요건(FR-045)은 "받은 문자열을 그대로 쓴다"로 충족된다. `Number()`나 `parseFloat()`가
한 번이라도 끼면 원칙 VI가 파일 출력 단계에서 무너지므로, `lib/csv.ts`는 문자열 연결만 한다.

쉼표를 포함할 수 있는 값(천 단위 구분이 들어간 표시용 문자열)은 따옴표로 감싼다. 다만 CSV에는
**표시용이 아닌 원본 정밀도 문자열**을 넣는다.

**Alternatives considered**:
- **서버가 CSV를 생성해 내려주기** → 정밀도는 확실하지만 같은 데이터를 두 번 조회하게 되고,
  화면에 보이는 것과 파일이 어긋날 여지가 생긴다. 기각.
- **표시용 형식(1,354.20)을 그대로 파일에 넣기** → 소수 2자리로 잘려 원본 정밀도가 사라진다.
  FR-045 위반. 기각.

## R2-8. 오늘 새로고침의 중복 방지와 수집 잠금의 분리

**Decision**: 기존 `fx_collection_lock` 테이블에 `scope` 컬럼을 더하고 기본 키를
`(scope, currency_code)`로 바꾼다. 수집은 `scope='collection'`, 새로고침은
`scope='today_refresh'`를 쓴다.

**Rationale**: FR-036a는 "새로고침이 수집 잠금과 독립"을, FR-036b는 "새로고침끼리는 하나만"을
요구한다. 현재 잠금 테이블의 기본 키는 `currency_code` 하나여서, 새로고침이 같은 테이블을
쓰면 수집과 충돌해 FR-036a를 어긴다.

범위 컬럼을 더하면 두 요구를 동시에 만족하면서 001이 세운 메커니즘(기본 키 INSERT 충돌 =
진행 중, 하트비트로 스테일 회수)을 그대로 재사용한다. 표준 SQL만 쓰므로 헌법의 DB 이식성
규약도 유지된다.

새 잠금 테이블을 만들지 않은 이유는 같은 개념이 두 벌이 되기 때문이다(원칙 IX).

**Alternatives considered**:
- **`asyncio.Lock`** → 단일 프로세스에서만 유효하다. 001의 R6가 같은 이유로 기각했고, 여기서도
  다중 워커 환경에서 중복 호출을 막지 못한다. 기각.
- **새로고침 전용 잠금 테이블 신설** → 동작하지만 획득·해제·스테일 회수 로직이 두 벌이 된다.
  기각.
- **중복 방지를 하지 않음** → 사용자가 버튼을 연타하면 호출이 그만큼 나간다. SC-008
  ("새로고침 1회 = 호출 1회")을 어긴다. 기각.

**스테일 회수 기준**: 새로고침은 수 초 내에 끝나므로 수집보다 짧은 만료를 쓴다. 값은
설정으로 선언한다.

## R2-9. 미구현 자산군 메뉴의 표현

**Decision**: 메뉴를 정적 정의로 두고 각 항목에 준비 여부를 표시한다. 준비되지 않은 항목은
링크를 걸지 않고 비활성 상태로 렌더링하며, **해당 라우트를 만들지 않는다.**

**Rationale**: FR-005는 "빈 화면이나 오류로 이어지지 않아야 한다"를 요구한다. 가장 확실한
방법은 이동할 경로를 아예 만들지 않는 것이다. 라우트를 만들고 안내 문구를 넣으면 화면이
하나 늘고, 그 화면이 자산군 구현 시 교체 대상이 된다.

헌법 원칙 IX와의 관계는 plan의 보충 판단에 적었다. 요약하면, 원칙이 금지하는 것은 여러
자산군의 **구현**을 벌여놓는 것이고 이번 설계는 다른 자산군의 코드를 한 줄도 만들지 않는다.

**Alternatives considered**:
- **각 자산군마다 "준비 중" 라우트 생성** → 화면이 6개 늘고 전부 폐기 예정이다. 기각.
- **미구현 메뉴를 아예 숨기기** → 사용자가 제품의 방향을 알 수 없고, 스크린샷의 정보 구조와
  어긋난다. 기각.

## R2-10. 001 화면 구조에서의 이관

**Decision**: 001의 4개 라우트를 다음과 같이 옮긴다.

| 001 | 002 | 비고 |
|-----|-----|------|
| `/` (조회) | `/fx` | 요약·차트·표가 합쳐진 분석 화면 |

**Rationale**: 사이드바 메뉴에 "수집 현황"이 없으므로(FR-002의 8개 항목에 없음) 별도 최상위
라우트로 두면 도달 경로가 사라진다. 수집은 외환에 종속된 운영 정보이므로 `/fx` 아래에 두고,
FR-049가 요구하는 셸 상단 표시기를 진입점으로 삼는다.

001의 컴포넌트는 대부분 재사용한다. `RateResult`·`NoQuoteResult`는 요약과 표로 역할이
나뉘므로 재구성이 필요하고, `FxChart`·`ChartTooltip`·`SpreadSettings`·`CollectionStatus`는
배치만 바뀐다.

**Alternatives considered**:
- **001 라우트를 남기고 새 화면을 병행** → 같은 기능이 두 곳에 존재해 유지보수가 갈라진다.
  명세의 목적(탭 이동 제거)에도 어긋난다. 기각.
- **수집 현황을 설정 아래로** → 설정은 사용자 환경 설정이고 수집은 운영 상태다. 성격이 다르다. 기각.
